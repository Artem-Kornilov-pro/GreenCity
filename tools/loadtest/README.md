# Нагрузочный прогон (Locust)

Сценарий — [`locustfile.py`](locustfile.py). Три типа пользователей, как на настоящем стенде:

| Пользователь | Что делает | Пауза между действиями |
|---|---|---|
| `Visitor` | открывает сайт: страница и её JS/CSS | 1–4 с |
| `ApiReader` | лёгкий API: `/api/health`, `/api/catalog`, `/api/layer-kinds` | 0,5–2 с |
| `Engineer` | рабочий цикл: загрузка DXF → GreenPlan → объяснения (Excel) → выгрузка DXF | 5–15 с |

Платные запросы (текст-обоснование, визуализации) и регистрация не делаются: это деньги и мусор в базе.

## Запуск

```bash
make loadtest HOST=https://baobab24.ru                       # веб-интерфейс Locust: http://localhost:8089
make loadtest-headless HOST=https://baobab24.ru              # ступени без интерфейса, отчёт в loadtest-report/
make loadtest-headless HOST=https://baobab24.ru USERS_CLASSES=ApiReader \
     LOAD_STEP_USERS=50 LOAD_STEP_SECONDS=30 LOAD_MAX_USERS=500 LOAD_THINK=0.2
```

- `LOAD_STEP_USERS`, `LOAD_STEP_SECONDS`, `LOAD_MAX_USERS` — ступени (по умолчанию +20 пользователей каждые 60 с до 200).
- `LOAD_THINK` — множитель пауз: `1` — как у человека, `0` — без пауз (предельный RPS).
- `USERS_CLASSES` — какие пользователи (`Visitor ApiReader Engineer`), по умолчанию все.
- `LOAD_DXF` — свой чертёж для `Engineer` (по умолчанию школьный участок, 116 КБ).

`make loadtest-headless` печатает таблицу по ступеням (`tools/loadtest/steps.py`): RPS, медиана и хвосты времени ответа, ошибки в секунду. Полный HTML-отчёт — `loadtest-report/report.html`.

### Лимиты по IP

Тяжёлые эндпоинты ограничены по IP (`backend/api/protection.py`): за 10 минут 30 разборов чертежа, 60 запусков GreenPlan, 30 выгрузок. Прогон с одной машины упирается в этот лимит: такие ответы видны в отчёте отдельной строкой с пометкой «[429 лимит]» и ошибкой не считаются. Строка «[503 очередь полна]» — очередь тяжёлых расчётов (`core/concurrency.py`) переполнена, это и есть предел сервера по расчётам.

Чтобы измерить тяжёлую часть без лимита, на время прогона на сервере задают `RATE_LIMIT_MULTIPLIER=0` (в `.env`, затем перезапуск бэкенда) — и обязательно возвращают обратно. Иначе прогон надо вести с нескольких адресов.

## Результаты: https://baobab24.ru, 19.10.2026

Сервер: 4 vCPU, 8 ГБ, продакшен-режим (3 процесса бэкенда, nginx). Клиент — один ноутбук (Locust 2.46.7, до 6 процессов), домашний канал; задержка сети до сервера ≈ 100 мс входит во все времена.

### Лёгкий API (`ApiReader`, паузы ×0,2)

| Пользователей | RPS | Медиана, мс | p95, мс | p99, мс | Ошибок/с |
|---:|---:|---:|---:|---:|---:|
| 50 | 105 | 150 | 370 | 510 | 0 |
| 100 | 216 | 150 | 260 | 440 | 0 |
| 150 | 305 | 190 | 340 | 580 | 0 |
| 200 | 379 | 220 | 490 | 650 | 0 |
| 250 | 419 (из них ≈ 372 успешных) | 280 | 730 | 930 | 47 |
| 300–500 | 620–1380 (из них ≈ 360–400 успешных) | — | — | — | 220–1000 |

**Предел — около 380–400 запросов в секунду.** До 200 пользователей ошибок нет; дальше лишние соединения обрываются на сетевом уровне («Connection reset by peer», «Broken pipe»), полезный поток не растёт. Ответов 5xx от приложения нет. Где именно рвутся соединения — прокси перед сайтом, защита хостинга или канал клиента, — по клиенту не различить: смотреть журналы nginx и Caddy на сервере во время прогона.

### Рабочий цикл (`Engineer`, 10 одновременно, без пауз)

| Запрос | 1 пользователь, медиана | 10 одновременно, медиана | 10 одновременно, p95 |
|---|---:|---:|---:|
| `POST /api/parse` (DXF 116 КБ) | 0,7 с | 1,5 с | 4,4 с |
| `POST /api/greenplan/generate` | 1,6 с | 3,2 с | 5,3 с |
| `POST /api/greenplan/explanations` (Excel) | 1,9 с | 3,5 с | 6,8 с |
| `POST /api/export-dxf` | 1,5 с | 2,3 с | 5,8 с |

Все 30 циклов, разрешённых лимитом по IP, прошли без ошибок и без отказов 503: расчёты встают в очередь, время ответа растёт примерно вдвое. Поток — около 3 тяжёлых запросов в секунду, это порядка 50 полных циклов в минуту на небольшом участке. На крупных реальных объектах (DWG Мосгеотреста) разбор и GreenPlan занимают десятки секунд, и предел соответственно ниже. После 30 циклов сервер отвечал «429» за 0,16 с — защита от одного адреса работает.

### Сайт (`Visitor`, 10 посетителей)

Без ошибок: ≈ 2,2 открытия сайта в секунду, ≈ 15 запросов в секунду и ≈ 3 МБ/с отдачи; страница — медиана 110 мс, JavaScript — медиана 290 мс, p95 1,1 с.

### Найдено по ходу

Страница входа заранее загружала чанки 3D-сцены (`three`, `react-three`, ≈ 1,2 МБ, ≈ 340 КБ в gzip): у `@react-three/fiber` своя копия `scheduler`, она попадала в чанк `react-three` вместе с React. Исправлено в `frontend/vite.config.ts` — теперь страница входа грузит только React и свой код, 3D догружается в редакторе.
