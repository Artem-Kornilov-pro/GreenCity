# GreenCity — техническая документация проекта

Справочник для того, кто должен разбираться в проекте и отвечать на вопросы по нему (демо/защита). Описывает состояние ветки `main`.

## 1. Что это

Сервис автоматического проектирования озеленения города с учётом подземных коммуникаций (хакатон ЛЦТ). Два независимых, но совместимых пути:

1. **Ручной редактор** — импорт DXF, 3D-просмотр, drag&drop объектов с проверкой норм, автогенерация по сетке, правка текстом через LLM, экспорт обратно в DXF.
2. **GreenPlan (issue #23)** — детерминированный конвейер, который предлагает озеленение участка по аналогии с реальными прошлыми проектами (retrieval), а не с нуля и не через ML-обучение.

Оба пути работают на одной и той же модели данных (`Scene`) и одном парсере DXF.

## 2. Архитектура

```
DXF-файл → parser/parse_dxf.py → Scene (JSON) → backend (FastAPI) → frontend (React + react-three-fiber, 3D)
```

- **backend/** — FastAPI, вся геометрия на `shapely`. Один процесс с `--reload` в деве (`UVICORN_WORKERS=1`), т.к. GIL не даёт параллелить CPU-геометрию потоками — для нагрузки нужны отдельные процессы.
- **frontend/** — React + TypeScript + react-three-fiber (3D-сцена), Vite dev server.
- **parser/** — `parse_dxf.py`, общее ядро для CLI и `/api/parse`.
- **converters/** — GeoJSON/SHP/DWG → DXF для внешних источников (Мосгеотрест и т.п.).
- **data/norms/** — нормативы в машиночитаемом виде, обособленно от кода (чтобы юрист/архитектор мог проверить число по первоисточнику, а не по Python).
- **locations/** — 14 реальных документированных проектов (`<slug>/<slug>.dxf` + `design_rationale.md`) + `location_old/` — синтетические фикстуры для тестов.
- **observability/** — Prometheus + Loki + Promtail + Grafana, поднимаются вместе со всем стеком.

Docker-compose поднимает 8 сервисов с healthcheck на каждом и `depends_on: condition: service_healthy` — backend стартует только когда mongo/redis реально приняли соединение. Код смонтирован volume'ами — правки в `backend/`/`parser/`/`frontend/` подхватываются на лету, без пересборки образа (новые зависимости в `requirements.txt` — нет, там нужен `--build`).

## 3. Модель данных: `Scene`

Единый JSON-контракт (`backend/schemas.py`) между парсером, обоими бэкенд-путями и фронтендом:

- `boundary` — граница участка (полигон).
- `restrictions` — зоны ограничений: `type` (sewer/gas/road/building/pedestrian_path/...), `severity` (`forbidden`/`warning`/`allowed`), `minDistance`, `polygon`.
- `objects` — точечные объекты сцены (деревья/кусты/здания/МАФ), с `type`, `position`, `metadata` (species, generated: true/false, provenance для GreenPlan).
- `windows`/`canopies`/`curbs` — декоративная геометрия (не самостоятельные объекты).

`severity`: `forbidden` — красный, сажать нельзя; `warning` — жёлтый, предупреждение (для ручного редактора — не запрет, для автогенератора — тоже запрет); `allowed` — зелёный, явно разрешённая зона (газон).

## 4. Парсер DXF (`parser/parse_dxf.py`)

Слои классифицируются **по подстроке в имени** (`POLYGON_RULES`, `POINT_LAYER_RULES`), не по жёсткой карте — имена слоёв не совпадают между проектами. Порядок правил значим (специфичное правило должно стоять раньше общего, иначе общее перехватит совпадение первым).

Ключевые приёмы, оплаченные реальными багами на конвертированных DXF:
- **Слияние по слою, не по сущности** (`_merge_corridors`/`_merge_polygon_zones`) — на реальных файлах один тип сети/газона может прийти тысячами мелких кусков; без слияния retrieval/zone_partitioning считали бы на россыпи вместо одной площади.
- **Коридоры труб/кабелей** — линии одного слоя буферизуются на `minDistance` и объединяются одним вызовом (`quad_segs=2` вместо 8 — экономия вершин на порядок при том же итоге).
- **Обрезка сетей по границе участка** (`_clip_offsite_zones`) — геоподоснова тянет сети далеко за пределы участка; без обрезки на узких вытянутых участках отступы перекрывали его насквозь.
- **Слаботочка vs силовой кабель** — разные нормы (warning vs forbidden), проверяется ДО общего правила `ELECTR`, иначе один тип "electrical" перекрывал большую часть площади из-за смешения проводов связи и питания.

## 5. Ручной редактор (backend)

| Эндпоинт | Что делает |
|---|---|
| `POST /api/parse` | DXF → `Scene` |
| `POST /api/generate-greenery` | Деревья/кусты/газон по сетке (без ML), см. ниже |
| `POST /api/edit-with-text` | Правка плана текстом через LLM |
| `POST /api/export-dxf` | `Scene` → DXF (зеркало парсера) |
| `GET /api/catalog` | Каталог видов/МАФ (кэш в Redis 30с) |

### 5.1 `/api/generate-greenery` (`greenery_generator.py`)

Детерминированный demo-генератор: сетка кандидатов с шагом `grid_spacing_m`, жадный отбор по `min_tree_spacing_m`, всё внутри `allowed`-зон минус запретные (расширенные на норматив отступа для вида посадки). Кусты — та же схема, но кандидаты это **центры групп** (по 3 куста вокруг, п.17 ТЗ "группировка"), с ограничением сверху (`MAX_GENERATED_BUSH_CLUSTERS=60`) и равномерным разбросом (`pick_spread`, k-средние), иначе двор "закатывается" кустами сплошным ковром. Газон — плитки без отступа по виду посадки (у дёрна нет корней/кроны).

Плотность — три рычага сразу: `grid_spacing_m`, размер зоны газона в конкретной сцене, `min_tree_spacing_m`. Универсального дефолта нет — параметр специально вынесен наружу под конкретную сцену.

### 5.2 Правка текстом (`llm_editor.py`) — ключевой архитектурный принцип: **LLM не считает координаты**

Два шага:
1. LLM получает JSON-контекст (контур участка, здания, ориентиры, кандидатные ряды, свободные области, выделенные пользователем зоны, каталог) и системный промпт, возвращает список операций (`add`/`remove`/`move`/`rotate`/`place_along`/`place_in_area`/`cover_area`/`connect`/`define_zone`/`design_area`/... — 18 типов) + текстовое объяснение.
2. Детерминированный `_PlanApplier` (поверх `placement.Placer`) выполняет каждую операцию: ищет ближайшую допустимую точку, раскладывает вдоль контура, строит маршрут в обход препятствий (граф видимости + Дейкстра для `connect`). Если операция невыполнима — не исключение, а запись в `rejected` с человекочитаемой причиной; одна сломанная операция от модели не роняет весь план.

`LLM_PROVIDER` — `gemini` (по умолчанию) или `yandex`, оба через OpenAI-совместимый клиент. Без ключа — `LlmNotConfiguredError` → 503, а не падение сервиса.

`design_area` — самый сложный оператор: `CourtyardDesigner` (`courtyard_design.py`) собирает целый двор одной операцией в порядке "от каркаса к деталям": выбор области (огорожена зданиями) → скелет дорожек (MST между входами) → мощение → фонтан/клумбы/фонари/лавки/изгородь/деревья вразброс/кусты вдоль дорожек.

## 6. GreenPlan (issue #23) — 7 этапов

| Этап | Модуль | Статус |
|---|---|---|
| 0. Справочники | `data/norms/` | Отступы готовы; xlsm-каталог видов/кодов решений — нет |
| 1. Импорт DWG→DXF | `parser/parse_dxf.py` | Готово; джойн ведомости с деревьями по номеру — нет |
| 2. Решения по существующим деревьям + компенсация | — | Не начато (ждёт внешних xlsm) |
| 3. Характеризация + retrieval | `site_characterization.py`, `pattern_retrieval.py` | Готово, корпус — 14 реальных проектов (не 20 из ТЗ) |
| 4. Назначение паттернов | `zone_partitioning.py`, `pattern_assignment.py` | Готово правилами; ранжирование LLM — нет |
| 5. Расстановка | `deterministic_placement.py` (поверх `placement.py`) | Готово |
| 6. Отчёт решений | `violation_report.py`, `assortment_report.py`, `decision_report.py` | Готово: нарушения + ассортимент + текст через локальную LLM |

Принцип на всех этапах: **LLM не считает координаты и не придумывает паттерн** — только (опционально) ранжирует уже отфильтрованный список.

### 6.1 Конвейер по шагам

1. `site_characterization.characterize_site(scene)` → `SiteCharacteristics` (площадь, доля пригодной площади, состав по типам зон, эвристика "двор/улица", честно помечена `territory_type_is_heuristic=True`).
2. `pattern_retrieval.nearest_projects()` → k ближайших проектов из 14 по косинусному сходству z-нормированного вектора признаков.
3. `zone_partitioning.partition_zones(scene)` → геометрические зоны участка: `building_border`/`path_corridor`/`site_edge`/`open_area`, по приоритету захвата площади.
4. `pattern_assignment.assign_patterns()` → для каждой зоны голосование k соседей (взвешено по сходству) за паттерн; `confidence = голоса победителя / k`; если ни один сосед не использовал такой вид зоны — паттерн по умолчанию с `confidence=0`, `source_project=None` (честно помечено как "не retrieval-результат").
5. `deterministic_placement.generate_for_scene()` → геометрия по 3 семействам паттернов: `linear` (ряд вдоль центральной линии), `clustered` (рощи/группы), `area_fill` (Пуассоновская заливка/сетка) — один параметризуемый алгоритм на семейство, не на паттерн. Проверка отступов **во время** расстановки через `Placer.is_free`, не постфактум.
6. `violation_report.find_violations()` → независимая проверка всех объектов сцены против всех зон (STRtree для отсечения кандидатов, точная геометрия для итогового решения — иначе на крупных участках O(объекты×зоны) уходил в 13+ секунд).
7. `assortment_report.summarize_assortment()` → сводка по видам/категориям только сгенерированных объектов.
8. `decision_report.generate_report()` → связный текст-объяснение через локальную LLM (Ollama/mistral:7b) по уже посчитанным решениям — LLM пересказывает факты человеческим языком, не считает и не придумывает.

### 6.2 API

`POST /api/greenplan/generate` — быстрый путь (доли секунды, без LLM): сцена + новые объекты + нарушения + ассортимент. `POST /api/greenplan/report` — отдельно текст-объяснение (~30с, локальная LLM) — разнесены специально, чтобы фронт не ждал текст ради уже готовой расстановки. Оба под `threading.Lock` — конкурентные тяжёлые запросы под одним GIL-процессом иначе не параллелятся, а тормозят друг друга (~11x).

### 6.3 Retrieval-корпус (`data/pattern_corpus.yaml`, `backend/pattern_corpus.py`)

14 реальных проектов (9 задокументированы изначально + 5 из ветки `new-convert`), каждый — реальный DXF + `design_rationale.md` с цитатой из реальной пояснительной записки, откуда взят паттерн. Честный меньший корпус вместо ожидания второго разработчика с 20 проектами по ТЗ. Самопроверка: каждый проект корпуса находит сам себя как ближайшего соседа (similarity=1.0) — базовый тест retrieval.

## 7. Каталог видов и МАФ (`plant_catalog.py`)

`CatalogItem`: семантика (`category`, `setback_kind`, `dimensions`) для генератора + внешний вид (`model`, `render`) для фронта. Есть `.glb` — рисуется модель; нет — примитив-заглушка по габаритам (штатный режим, не баг). `catalog_generated.json` — записи из реальных паков моделей (`tools/convert_models.mjs`), дополняет статический каталог, не заменяет.

## 8. Аутентификация и проекты

JWT access (15 мин) + refresh (30 дней, сессия в Redis — реальный отзыв при logout). MongoDB — только `users`/`projects` (постоянное состояние); Redis — то, что не жалко потерять (rate-limit, кэш каталога, сессии). **Fail-open**: недоступен Redis — лимиты/сессии не блокируют работу; недоступна MongoDB — только `/api/projects`/`/api/auth/*` отвечают 503, сам редактор (DXF/генерация/правка текстом) не зависит от БД вовсе. Лимит — 3 проекта на пользователя.

## 9. Экспорт DXF (`export_dxf.py`)

Зеркало парсера, не идеальный round-trip: те же слои-подстроки (`TREE`/`BUSH`/`LAMP`...), объекты с `width`+`depth` (мощение/газон/изгородь) экспортируются реальным прямоугольником, не точкой. Сгенерированные GreenPlan объекты — слой с префиксом `NEW_` (issue #23: разделить "сохранённое" и "новую посадку"). Severity зон кодируется цветом (AutoCAD Color Index) + XDATA.

## 10. Тесты

571 тест. Два семейства фикстур: **синтетические** (`backend/tests/helpers.py`) — точная геометрия для точных assert'ов; **реальные** — `locations/location_old/` (быстрые синтетические участки для юнит-тестов) и полный корпус из 14 (`locations/*`) для честной проверки "расстановка реально не нарушает нормы" на настоящих данных, не только на синтетике. MongoDB/Redis замоканы (`mongomock_motor`/`fakeredis`), LLM в тестах никогда не вызывается по-настоящему (env-переменные ключей стираются автоматически).

## 11. Наблюдаемость

Prometheus (HTTP + бизнес-метрики: парсинги/генерации/экспорты по типу, исходы LLM-правки и GreenPlan-отчёта, регистрации/входы, блокировки rate-limit) + Loki/Promtail (JSON-логи с request_id) + готовые дашборды Grafana. Всё поднимается одной командой вместе с основным стеком, деградация observability не роняет сам сервис.

## 12. Частые вопросы (для защиты)

**Почему не ML/нейросеть?** Датасет — единицы-десятки реальных проектов, для полноценного обучения этого недостаточно и негде проверить обобщение. Вместо этого — retrieval (поиск похожих реальных решений) + детерминированная геометрия; LLM — только для (опционального) ранжирования уже отфильтрованных вариантов и для пересказа готовых фактов человеческим языком, никогда не для координат/паттернов с нуля.

**Что если LLM недоступна?** Текстовая правка отвечает понятной ошибкой (503), GreenPlan отчёт — `report=null` с `report_error`, сама расстановка (детерминированная часть) не страдает.

**Что если нет данных о посадке (620-ПП/xlsm)?** Этап 2 (компенсация за вырубку) не реализован — ждёт данных, которых нет в открытом доступе; честно отражено в статусной таблице, не имитируется.

**Как проверяется, что паттерн реально подходит участку?** Retrieval — по числовым признакам (площадь, доля пригодной площади, состав зон), не текстом; назначение паттерна — голосование k ближайших соседей, а не один "самый похожий" проект; итоговая расстановка проверяется независимым модулем нарушений (`violation_report.py`), а не тем же кодом, что её строил.

**Почему 14 проектов, а не 20 из ТЗ?** Полный корпус из 20 — задача второго разработчика, ещё не восстановлен. 14 — честное подмножество из того, что реально задокументировано (реальный DXF + реальная пояснительная записка), не заглушка.
