# GreenCity — техническая документация проекта

Справочник для того, кто должен разбираться в проекте и отвечать на вопросы по нему (демо/защита). Описывает состояние ветки `main`. Документация решения по ТЗ (MVP, BPMN, интерпретируемость, библиотеки, проверка DXF, ограничения) — [SOLUTION.md](SOLUTION.md), алгоритм GreenPlan подробно — [GREENPLAN_ALGORITHM.md](GREENPLAN_ALGORITHM.md).

## 1. Что это

Сервис автоматического проектирования озеленения города с учётом подземных коммуникаций (хакатон ЛЦТ). Два независимых, но совместимых пути:

1. **Ручной редактор** — импорт DXF, 3D-просмотр, drag&drop объектов с проверкой норм, автогенерация по сетке, правка текстом через LLM, экспорт обратно в DXF.
2. **GreenPlan** — детерминированный конвейер, который предлагает озеленение участка по аналогии с реальными прошлыми проектами (retrieval), а не с нуля и не через ML-обучение.

Оба пути работают на одной и той же модели данных (`Scene`) и одном парсере DXF.

## 2. Архитектура

```
DXF-файл → parser/parse_dxf.py → Scene (JSON) → backend (FastAPI) → frontend (React + react-three-fiber, 3D)
```

- **backend/** — FastAPI, вся геометрия на `shapely`. Все обработчики асинхронные: тяжёлые расчёты идут в пуле потоков через ограниченную очередь, запросы к LLM — асинхронным клиентом (раздел 2.1). В деве — один процесс с `--reload` (`UVICORN_RELOAD=1`, `UVICORN_WORKERS=1`); в продакшене (`docker-compose.prod.yml`, образ по умолчанию) — `UVICORN_WORKERS` процессов без `--reload`, т.к. GIL не даёт параллелить CPU-геометрию потоками — для нагрузки нужны отдельные процессы. Ответы сжимаются (`GZipMiddleware`). Наружу бэкенд не открыт: к нему обращается только прокси фронтенда. Код разложен по пакетам (карта ниже).
- **frontend/** — React + TypeScript + react-three-fiber (3D-сцена); в деве — Vite dev server, в продакшене — статическая сборка за nginx (`frontend/Dockerfile.prod`, `/api/` проксируется на backend). Страница редактора — `src/pages/editor/`: страница, панели (топбар, левая панель, Ассистент, GreenPlan, диалог сохранения) и хуки `hooks/` (импорт сцены и перетаскивание файлов, правка объектов, GreenPlan, ассистент, экспорт, проект). Сессия и последние параметры GreenPlan — в Redux (`src/store/`), все запросы — через общий клиент `src/lib/http.ts`: разбор ошибок FastAPI, обновление токена при 401, повтор GET при сетевой ошибке и 502/503/504; тяжёлые POST не повторяются.
- **parser/** — `parse_dxf.py` (сборка сцены и командная строка) + `dxf_parsing/` (правила слоёв, геометрия, зоны и граница, здания и точечные объекты), общее ядро для CLI и `/api/parse`.
- **converters/** — GeoJSON/SHP/DWG → DXF для внешних источников (Мосгеотрест и т.п.).
- **data/norms/** — нормативы в машиночитаемом виде, обособленно от кода (чтобы юрист/архитектор мог проверить число по первоисточнику, а не по Python).
- **locations/** — корпус GreenPlan: 14 реальных документированных проектов и 20 синтетических эталонов (`<slug>/<slug>.dxf` + `design_rationale.md`) + `location_old/` — синтетические фикстуры для тестов + `location_test/` — три тестовых участка для приёмки с примерами результата.
- **observability/** — Prometheus + Loki + Promtail + Grafana, поднимаются вместе со всем стеком.

### 2.1 Асинхронность, очередь расчётов, защита и сеть

**Асинхронность.** Все эндпоинты — `async def`, event loop не блокируется ничем тяжёлым:

| Работа | Как выполняется |
|---|---|
| Геометрия и документы (разбор DXF, GreenPlan, экспорт, объяснения, записка, генерация по сетке, контекст и применение плана ассистента) | `core/concurrency.run_heavy` — пул потоков с тяжёлым слотом |
| Разбор и экспорт пачки DWG | отдельный процесс через `asyncio.create_subprocess_exec`; слот пачки (`fcntl.flock` на весь контейнер) ждётся через `asyncio.sleep`, поток не занимается |
| Запросы к LLM (ассистент, текст-обоснование) | `openai.AsyncOpenAI`: таймаут 120 и 60 с, один повтор; тяжёлый слот не держится |
| MongoDB, Redis | асинхронные клиенты (`AsyncMongoClient`, `redis.asyncio`); bcrypt — в `asyncio.to_thread` |
| Чтение и запись файлов (загрузки, хранилище исходников) | `run_light` — пул потоков без слота |

Правка текстом проходит три шага. Сначала проверяется ключ модели, чтобы без него не считать геометрию. Затем в тяжёлом слоте строится контекст. Потом слот освобождается на время ответа модели и снова занимается для применения плана.

**Очередь расчётов** (`core/concurrency.py`). Потоки одного процесса делят GIL, и два расчёта параллельно идут не быстрее, а вдвое медленнее каждый. Поэтому на процесс uvicorn — `HEAVY_CONCURRENCY` (1) расчёт одновременно, остальные ждут в очереди. Очередь ограничена:

- больше `HEAVY_QUEUE_MAX` (8) ждущих или ожидание дольше `HEAVY_WAIT_S` (120 с) — ответ 503 с `Retry-After`;
- лёгкие запросы (health, каталог, вход, проекты) в очереди не стоят;
- замер: во время расчёта GreenPlan `/api/health` отвечает за доли миллисекунды; из 12 одновременных запросов GreenPlan 9 выполняются по очереди, 3 получают 503.

**Защита тяжёлых эндпоинтов** (`api/protection.py`):

| Механизм | Что делает |
|---|---|
| Лимит частоты с одного IP за 10 минут | parse — 30, parse_dwg — 10, greenplan (generate, document, explanations) — 60, llm (edit-with-text, greenplan/report) — 30, export — 30, generate (generate-greenery) — 30. Сверх — 429 с `Retry-After`. Фиксированное окно в Redis; без Redis лимит не действует (fail open). Все лимиты умножаются на `RATE_LIMIT_MULTIPLIER` (0 — выключить) |
| Лимит размера тела (`BodySizeLimitMiddleware`) | загрузка DXF и DWG — `MAX_UPLOAD_MB` (200), прочие запросы — `MAX_BODY_MB` (64). По `Content-Length` отказ сразу, без него — по мере чтения тела. Ответ 413 |
| Число файлов DWG | не больше `MAX_DWG_FILES` (60) за загрузку, иначе 400 |
| Уже было раньше | длина просьбы ассистенту — до 2000 символов, история — до 20 правок; `k` у GreenPlan — от 1 до 9; разбор DWG — не дольше 15 минут |

**Сеть.**

- Наружу опубликованы только фронтенд и Grafana. Бэкенд, MongoDB, Redis, Prometheus и Loki слушают только сеть compose.
- Браузер обращается к API по относительным путям `/api/…` на адрес сайта. В дев-режиме их проксирует vite (`frontend/vite.config.ts`, `API_PROXY_TARGET`), в продакшене — nginx (`frontend/nginx/default.conf.template`).
- CORS выключен; при фронтенде на другом домене разрешённые адреса задаются в `CORS_ALLOW_ORIGINS`.
- uvicorn запущен с `--proxy-headers`, поэтому IP клиента для лимитов берётся из `X-Forwarded-For` прокси. Доверять заголовку безопасно, потому что к бэкенду никто, кроме прокси, не подключается.
- Swagger (`/docs`, `/openapi.json`) открыт при `API_DOCS=1` (дев, через фронтенд — `http://localhost:5173/docs`), в продакшене выключен.

Docker-compose поднимает 8 сервисов с healthcheck на каждом и `depends_on: condition: service_healthy` — backend стартует только когда mongo/redis реально приняли соединение. Код смонтирован volume'ами — правки в `backend/`/`parser/`/`frontend/` подхватываются на лету, без пересборки образа (новые зависимости в `requirements.txt` — нет, там нужен `--build`). Для сервера — `docker-compose.prod.yml` поверх основного файла (`make docker-prod-up`): статика за nginx на :80, backend без смонтированного кода и `--reload` (3 процесса, 3 ядра, до 4 ГБ; до 2 пачек DWG одновременно), кеш MongoDB 0,5 ГБ, ротация логов контейнеров; рассчитан на сервер 4 vCPU / 8 ГБ / 40 ГБ SSD (README, «Docker на сервере»).

## 3. Модель данных: `Scene`

Единый JSON-контракт (`backend/core/schemas.py`) между парсером, обоими бэкенд-путями и фронтендом:

- `boundary` — граница участка (полигон).
- `restrictions` — зоны ограничений: `type` (sewer/gas/road/building/pedestrian_path/...), `severity` (`forbidden`/`warning`/`allowed`), `minDistance`, `polygon`.
- `objects` — точечные объекты сцены (деревья/кусты/здания/МАФ), с `type`, `position`, `metadata` (species, generated: true/false, provenance для GreenPlan).
- `windows`/`canopies`/`curbs` — декоративная геометрия (не самостоятельные объекты).
- `lawns` — газон (`LawnArea`): полигон с дырками (клумбы кустарника), `area_sqm`, `status` (`new` — устройство газона, `existing` — сохраняемый). Сохраняемый газон со слоёв газона чертежа приходит сразу из `/api/parse` и `/api/parse-dwg` (`exchange/dxf_parser.complete_scene`), новый добавляет GreenPlan.

`severity`: `forbidden` — красный, сажать нельзя; `warning` — жёлтый, предупреждение (для ручного редактора — не запрет, для автогенератора — тоже запрет); `allowed` — зелёный, явно разрешённая зона (газон).

## 4. Парсер DXF (`parser/parse_dxf.py`)

Слои классифицируются **по подстроке в имени** (`POLYGON_RULES`, `POINT_LAYER_RULES`), не по жёсткой карте — имена слоёв не совпадают между проектами. Порядок правил значим (специфичное правило должно стоять раньше общего, иначе общее перехватит совпадение первым).

Ключевые приёмы, оплаченные реальными багами на конвертированных DXF:

- **Слияние по слою, не по сущности** (`_merge_corridors`/`_merge_polygon_zones`) — на реальных файлах один тип сети/газона может прийти тысячами мелких кусков; без слияния retrieval/zone_partitioning считали бы на россыпи вместо одной площади.
- **Вид растения из имени слоя.** Слой с названием вида из справочника («ЛИПА МЕЛКОЛИСТНАЯ») даёт объекту `metadata.species`, бэкенд (`exchange/dxf_parser.py`) по нему подставляет `catalogId` — объект получает 3D-модель и габариты своего вида, а характеристика участка — состав существующих пород.
- **Невалидные контуры чинятся, а не отбрасываются** (`core/shapes.py::polygon_from_points`, `make_valid`) — одно правило для расстановки, газона, разбиения на зоны, признаков участка, проверки нарушений и генератора по сетке. Раньше часть модулей молча пропускала самопересекающиеся контуры из DXF: на 20_makeeva_s терялось 140 тыс. м² разрешённой земли (GreenPlan не сажал ни одного дерева), а 113 тыс. м² запретных зон не видела проверка нарушений.
- **Коридоры труб/кабелей** — линии одного слоя буферизуются на `minDistance` и объединяются одним вызовом (`quad_segs=2` вместо 8 — экономия вершин на порядок при том же итоге).
- **Обрезка сетей по границе участка** (`_clip_offsite_zones`) — геоподоснова тянет сети далеко за пределы участка; без обрезки на узких вытянутых участках отступы перекрывали его насквозь.
- **Дальние здания отбрасываются** (`parse_dxf._clip_offsite_buildings`) — топоплан пачки DWG приносит квартал вокруг участка (на Харьковской — 38 зданий до 660 м от границы работ). Остаются здания, которые хоть краем заходят в полосу 20 м от границы: только они дают отступ посадкам. Вместе с дальним зданием уходят его зона, окна и козырьки.
- **Земля под сценой** — приглушённо-зелёное основание участка (газон ярче него), под ним — земля окрестностей только там, где в чертеже что-то есть: площадка 4 м вокруг каждого дома и полотна улиц и дорожек (`geometry.computeSurroundings`, `frontend/src/scene/Ground.tsx`). Соседние дома у границы не висят в пустоте, а сцена не расширяется заливкой пустого места.
- **Слаботочка vs силовой кабель** — разная серьёзность зоны (warning vs forbidden) и ширина охранного коридора, проверяется ДО общего правила `ELECTR`, иначе один тип "electrical" перекрывал большую часть площади из-за смешения проводов связи и питания. Отступ посадки от них при этом одинаковый (2 м дерево, 0,7 м куст — одна строка табл. 9.1 СП 42).
- **Маркер точки ≠ второй объект** — экспорт пишет каждую посадку как `POINT` + маленький `CIRCLE` (иначе в CAD её не видно); круг ровно в точке `POINT`/`INSERT` того же слоя парсер считает маркером. Без этого повторная загрузка экспортированного плана удваивала все посадки (найдено сквозным тестом).

| `POST /api/parse` | DXF → `Scene` |
| `POST /api/parse-dwg` | Папка из нескольких `.dwg` → `Scene`: батч-конвертация через `dwg2dxf`/LibreDWG + слияние в один документ (`backend/exchange/dwg_batch_converter.py`), дальше тот же `parse_dxf.py`. | `POST /api/export-dxf` | `Scene` → DXF: слои результата поверх исходного чертежа (раздел 9) |
| `GET /api/catalog` | Каталог видов/МАФ (кэш в Redis 30с) |

### 5.1 `/api/generate-greenery` (`generation/`)

Детерминированный генератор: кандидаты деревьев — Poisson-disk разброс с радиусом `grid_spacing_m` (без рядов сетки, с фиксированным сидом), жадный отбор по `min_tree_spacing_m`, пятна гуще и реже посадки и смесь видов (`natural_sampling.py`); всё внутри `allowed`-зон минус запретные (расширенные на норматив отступа для вида посадки). Кусты — регулярная сетка, но её узлы — **центры групп** (по 3 куста вокруг, п.17 ТЗ "группировка"), с ограничением сверху (`MAX_GENERATED_BUSH_CLUSTERS=60`) и равномерным разбросом (`pick_spread`, k-средние), иначе двор "закатывается" кустами сплошным ковром. Газон — плитки без отступа по виду посадки (у дёрна нет корней/кроны).

Плотность — три рычага сразу: `grid_spacing_m`, размер зоны газона в конкретной сцене, `min_tree_spacing_m`. Универсального дефолта нет — параметр специально вынесен наружу под конкретную сцену.

### 5.2 Правка текстом (`text_editor/service.py`) — ключевой архитектурный принцип: **LLM не считает координаты**

Два шага:

1. LLM получает JSON-контекст (`text_editor/prompt.py`: контур участка, здания, ориентиры, кандидатные ряды, свободные области, выделенные пользователем зоны, каталог) и системный промпт, возвращает список операций (`text_editor/operations.py`: `add`/`remove`/`move`/`rotate`/`place_along`/`place_in_area`/`cover_area`/`connect`/`define_zone`/`design_area`/`run_greenplan`/... — 21 тип) + текстовое объяснение.
2. Детерминированный `PlanApplier` (`text_editor/applier.py` + `ops_placement.py` + `ops_editing.py`, поверх `core.placement.Placer`) выполняет каждую операцию с учётом отступов по породе: ищет ближайшую допустимую точку, раскладывает вдоль контура, строит маршрут в обход препятствий (граф видимости + Дейкстра для `connect`). Если операция невыполнима — не исключение, а запись в `rejected` с человекочитаемой причиной; одна сломанная операция от модели не роняет весь план.

Каталог в контексте: базовые позиции (МАФ, газон, мощение) — все, виды — выборкой по классу формы (сначала базовый ассортимент 515-ПП), всегда с русским названием. Виды, названные в просьбе («липы», «клёны», «туи»), попадают в контекст сверх выборки: `prompt.mentioned_species` сравнивает слова просьбы с названиями видов с учётом окончаний. Без этого модель не находила липу мелколистную среди 220 видов и сажала что-то похожее по размеру.

История чата: фронтенд отправляет прошлые правки (`history`: просьба, ответ, что сделано), модель получает последние четыре в сокращённом виде. Так понимаются отсылки «убери их», «то же самое у второго дома». Отменённые правки в историю не попадают.

`run_greenplan` — мост к GreenPlan: на «озелени участок в регулярном стиле, побольше лип» модель выбирает параметры GreenPlan (стиль, что сажать, предпочтительные виды, дорожки, освещение, скамейки). Бэкенд проверяет виды (только `species_*` своей категории) и возвращает параметры в `greenplan` ответа, а фронтенд запускает настоящий GreenPlan на сцене ответа — с его панелью решений, нарушениями и запиской.

Последнюю правку ассистента можно отменить кнопкой в чате, пока план после неё не менялся (сцена до и после хранится на фронтенде; ручная правка после неё отмену убирает, чтобы не стереть её молча).

Отбор существующих объектов (`remove_where`, `replace_where`, `thin_out`, `resize`, `face`, `align_along`, `set_count`) кроме места (у цели, в радиусе от точки) фильтрует по виду (`species`: «Клен» — любой клён, «Клен остролистный» — только он; падеж и ё не важны, `plan_common.name_matches`; у объектов без вида — по русскому названию типа: «шезлонг», «урна») и по id (`ids`). В историю чата уходят id объектов, созданных каждой правкой, — «убери их», «сделай их поменьше» трогают ровно их, а не всё в радиусе от места посадки. Подъезды в контексте — с номером («подъезд 1») и id, чтобы на них можно было сослаться. Урны из чертежа (тип `urn`) и из каталога (`trash`) — один тип. Правки без удаления (масштаб, замена, разворот), не нашедшие объектов у точки, расширяют круг до ближайших и пишут об этом; удаление так не делает.

Честность ответа: поля, которые операция не поддерживает, не отбрасываются молча, а попадают в предупреждения; если не выполнено ничего, ответ модели («площадка огорожена») заменяется на «Не получилось: …» с причиной; под ответом в чате — что реально сделал планировщик.

Оценка на настоящей модели — `tools/ai_editor_eval/` (`.venv/bin/python tools/ai_editor_eval/run.py [id …]`): 29 реалистичных просьб на трёх участках (пустой двор, двор с детской площадкой, реальный проект на 600+ объектов), включая цепочки с отсылками («посади 4 берёзы…» → «а теперь убери их»), вопросы, опечатки и несуществующий вид. Каждая проверяется объективно по сцене (что добавлено/удалено, какие виды, где, нарушения норм у новых объектов). Каждый случай — платный запрос (~11–28 тыс. токенов), в тесты не входит; найденные провалы воспроизведены офлайн в `backend/tests/text_editor/test_editor_polish.py`. Результат доводки: 14/24 → 29/29.

`LLM_PROVIDER` — `yandex` (по умолчанию: Yandex AI Studio, `core/yandex_ai.py`, модель `YANDEX_CLOUD_MODEL` — по умолчанию Qwen3 235B A22B: строгий JSON по длинной инструкции и без рассуждений, которые съедают лимит ответа) или `gemini`, оба через OpenAI-совместимый клиент. Без ключа — `LlmNotConfiguredError` → 503, а не падение сервиса.

`design_area` — самый сложный оператор: `CourtyardDesigner` (`text_editor/courtyard_design.py`, выбор области и каркас дорожек — `courtyard_layout.py`) собирает целый двор одной операцией в порядке "от каркаса к деталям": выбор области (огорожена зданиями) → скелет дорожек (MST между входами) → мощение → фонтан/клумбы/фонари/лавки/изгородь/деревья вразброс/кусты вдоль дорожек. Виды, которые модель не назвала сама (`tree_ids`/`bush_ids`), подбирает `species_selection.courtyard_palette()` — тот же подбор, что у GreenPlan, для дворовой территории: три дерева разных родов из ассортимента Москвы с приоритетом базового ассортимента 515-ПП и вид для изгороди вдоль дорожек (без колючих и чувствительных к реагентам).

### 6.1 Конвейер по шагам

1. `site_characterization.characterize_site(scene)` → `SiteCharacteristics` (площадь, доля пригодной площади, состав по типам зон, тип территории по правилам: двор / улица / площадь / парк-сквер / промышленная-охранная / не определён — только «не определён» помечен `territory_type_is_heuristic=True`).
2. `pattern_retrieval.nearest_projects()` → проекты корпуса (34), упорядоченные по косинусному сходству z-нормированного вектора признаков (алгоритм подробно — раздел 6.2 ниже).
3. `zone_partitioning.partition_zones(scene)` → геометрические зоны участка: `building_border`/`path_corridor`/`site_edge`/`open_area`, по приоритету захвата площади.
4. `pattern_assignment.assign_patterns()` → решение в два уровня: сначала общее на участок, потом по зонам — чтобы у участка был единый стиль.

   **Общее решение на участок.** У каждого приёма есть стиль (`PatternSpec.style`):
   - регулярный — диагональные ряды, боскет, треугольная сетка, концентрические кольца;
   - пейзажный — волнистые ряды, рощи, свободный разброс;
   - нейтральный — изгородь вдоль дорожки и кольцо у здания (бывают в любом стиле), заливка без замысла.

   Стиль участка выбирают k самых похожих проектов (сходство не ниже `MIN_VOTE_SIMILARITY = 0.2`), у которых для видов зон этого участка есть решение регулярного или пейзажного стиля; голос весит столько, сколько сходство. Ведущий проект — самый похожий проект победившего стиля. Стиль и ведущий проект записываются в каждое решение (`site_style`, `lead_project`) и выводятся первыми в записке, на панели GreenPlan и в тексте-обосновании.

   Проект только с нейтральными решениями в голосовании за стиль не участвует, и стиль решают следующие по сходству. Поэтому у уличных эталонов, ближайших к типовым дворам, во дворах есть приёмы определённого стиля: боскет у 31, сад по треугольной сетке у 35. Без них стиль решали дальние, в основном пейзажные проекты: из 14 реальных проектов определённый стиль есть у семи, и только один из них регулярный. В итоге все шесть тестовых участков выходили пейзажными, теперь их 3 регулярных и 3 пейзажных.

   Зачем: проекты корпуса описаны частично — в основном одним-двумя видами зон. Без общего шага каждый вид зоны голосовал сам по себе, и участок собирался из приёмов трёх-четырёх проектов разного стиля: в одном дворе волны, диагональные ряды и заливка одновременно.

   **Решения по зонам** — голосование отдельно по каждому виду зоны:
   - **кто голосует:** k самых похожих проектов, у которых есть решение для этого вида зоны в стиле участка или нейтральное (проект без такой записи место избирателя не занимает), со сходством не ниже `MIN_VOTE_SIMILARITY`; заливка без замысла (`generic_fill`) голосует, только если других решений нет;
   - **вес голоса** — сходство проекта с участком;
   - **раздача зон:** зоны одного вида делятся между паттернами избирателей по площади, пропорционально весу голосов: крупнейшая зона — самому весомому паттерну, каждая следующая — паттерну, сильнее всех недобравшему свою долю площади. Если избиратели согласны, все зоны вида получают один приём; раньше один победитель забирал все зоны вида, и участок заливался одним приёмом;
   - **источник:** `source_project` — самый похожий проект среди голосовавших за паттерн зоны, `confidence` — доля избирателей, голосовавших за этот паттерн;
   - **нет избирателей** — типовой приём стиля участка (`pattern_library.default_pattern`: для открытых зон регулярного участка — треугольная сетка, пейзажного — рощи) с `confidence=0`, `source_project=None`; в записке — «типовое решение в стиле участка — проверить».
5. `deterministic_placement.generate_for_scene()` → геометрия по 3 семействам паттернов: `linear` (ряд вдоль центральной линии), `clustered` (рощи/группы), `area_fill` (Пуассоновская заливка/сетка) — один параметризуемый алгоритм на семейство, не на паттерн. Проверка отступов **во время** расстановки через `Placer.is_free`, не постфактум; кандидаты площадной заливки и рощ заранее отсеиваются от занятых существующими объектами точек, иначе на участке с сотнями старых деревьев центр рощи попадал к старому дереву и вся группа отклонялась. Виды растений подбирает `species_selection.select_site_species()` — единая палитра на участок: пары (вид зоны, паттерн) идут по убыванию площади, крупнейшие задают палитру, следующие берут из неё виды своей формы и добавляют новые, только пока в палитре меньше 4 деревьев и 4 кустарников (предел мягкий: роль, которой по форме не подходит ни один вид палитры, получает свой). Фильтры для каждого вида: только виды из ассортимента для озеленения Москвы с «+» для типа территории участка, без инвазивных (369-ПП), без кодов ассортимента, запрещающих место (самосев; у детских площадок; у дорожек — чувствительные к реагентам), без колючих вдоль дорожек (СП 82 п. 9.22), без широкой кроны в полосе у здания (743-ПП). Форма — по морфологической группе вида под роль паттерна (изгородь и аллея — один вид, роща и свободная посадка — смесь разных родов); приоритет — базовый ассортимент 515-ПП для дворов, затем основной ассортимент. Выбор и его основание попадают в `ZoneAssignment` (`tree_species`/`bush_species`/`species_basis`) и в текст отчёта.
   Объём ограничен: не больше 400 деревьев и 400 кустов на зону (`MAX_OBJECTS_PER_ZONE`; у рядов — за счёт шага, чтобы ряды оставались по всей зоне) и не больше 10 000 новых посадок на участок (`MAX_NEW_OBJECTS_PER_SITE`; сверх — равномерное прореживание с сохранением доли каждой зоны). Без этого крупные участки давали десятки тысяч объектов (02_peschany — 54 тыс., 05_klykova — 54 тыс.).
6. `lawn.plan_lawns()` → газон (раздел 6.5): площадь, а не объекты.
7. `violation_report.find_violations()` → независимая проверка всех объектов сцены против всех зон (STRtree для отсечения кандидатов, точная геометрия для итогового решения — иначе на крупных участках O(объекты×зоны) уходил в 13+ секунд).
8. `assortment_report.summarize_assortment()` + `lawn_assortment()` → сводка по видам/категориям только сгенерированных объектов (шт.) и строка нового газона (м²).
9. `decision_report.generate_report()` → связный текст-объяснение через YandexGPT 5.1 Pro в Yandex AI Studio (Responses API; тот же ключ и каталог, что у ИИ-ассистента, модель — `YANDEX_CLOUD_REPORT_MODEL`) по уже посчитанным решениям — LLM пересказывает факты человеческим языком, не считает и не придумывает.

### 6.2 Как работает поиск похожих проектов (`backend/greenplan/pattern_retrieval.py`)

Не ML и не обучение с градиентом — k ближайших соседей по косинусному сходству вектора числовых признаков. Это и есть "обучение" при малом N (34 проекта): не выдумываем решение с нуля, а смотрим, что реально делали архитекторы на похожих участках.

1. **Вектор признаков** (`_raw_vector`) собирается из `SiteCharacteristics`: `plantable_ratio` (доля пригодной площади), `log1p(площадь участка)` (лог — иначе огромный разброс площадей задавил бы остальные признаки), `building_count`, доли каждого типа зоны ограничений от фиксированного списка `KNOWN_ZONE_TYPES` (building/road/pedestrian_path/gas_pipeline/sewer/water_pipeline/electrical/playground_zone — только эти 8, зона другого типа в вектор не попадает и не искажает доли известных), one-hot `territory_type` (шесть категорий) — добавляется, только если `territory_type_is_heuristic == False`, то есть для любого определённого типа территории; «не определён» в вектор не попадает.
2. **Стандартизация (z-score)** по статистике самого корпуса (`_corpus_matrix`, среднее/std считаются один раз и кэшируются `lru_cache`) — без неё `log1p(площадь)` (порядок 5–12) забил бы `plantable_ratio` (порядок 0–1) в косинусном расстоянии почти до нуля. Стандартизуются и корпус, и вектор нового участка одними и теми же mean/std корпуса.
3. **Косинусное сходство** между стандартизованным вектором участка и каждым проектом корпуса (`nearest_projects()`); признак, постоянный по всему корпусу (std=0), не делится на ноль (заменяется на 1.0).
4. Возвращаются `k` (по умолчанию 3) проектов с наибольшим сходством — список `NeighborMatch(slug, similarity)`, по убыванию.

Дальше ближайшие проекты идут в `pattern_assignment.py` как избиратели за паттерн для каждого вида зоны (голосование, взвешенное по `similarity`, с порогом сходства, см. п.4 конвейера выше) — само сходство участков не выбирает паттерн напрямую, только формирует, кто и с каким весом голосует.

**Проверка корректности**: каждый из 34 проектов корпуса, поданный как "новый участок", должен находить сам себя ближайшим соседом с `similarity = 1.0` — это базовый регрессионный тест retrieval (если он ломается — либо вектор признаков считается по-разному для корпуса и запроса, либо стандартизация рассинхронизировалась).

### 6.3 API

`POST /api/greenplan/generate` — быстрый путь (секунды, без LLM): тело `{scene, options}` (параметры — раздел 6.6), ответ — сцена с результатом, решения по зонам, нарушения, ведомость посадок, ведомость благоустройства (`improvements`) и замечания к параметрам (`notes`). Повторный запуск заменяет прошлый результат GreenPlan в присланной сцене, а не добавляет второй слой (`greenplan/pipeline.py`). `POST /api/greenplan/report` — отдельно текст-объяснение (YandexGPT, секунды) — разнесены специально, чтобы фронт не ждал текст ради уже готовой расстановки. Расстановка идёт через очередь расчётов (раздел 2.1): конкурентные тяжёлые запросы под одним GIL-процессом не параллелятся, а тормозят друг друга (~11x). Текст-обоснование — асинхронный запрос к модели, очередь не занимает.

`POST /api/greenplan/explanations?format=json|csv` — объяснение каждой посадки со ссылкой на НПА и пункт, отклонённые кандидаты и зоны запрета (раздел 9.1).

`POST /api/greenplan/document` — пояснительная записка в DOCX (`greenplan/document.py`) по текущей сцене и решениям GreenPlan — «сценарий выгрузки документации» из ТЗ. Разделы: сведения об участке, нормативная база и применённые отступы (в т.ч. по породе), принятые решения с происхождением каждого («по аналогии с проектом X» / «типовое решение — проверить»), проекты-аналоги с цитатами, ведомость элементов озеленения по форме 9 ГОСТ 21.508-2020, проверка норм (нарушения новых посадок — поимённо, существующих — сводкой по видам ограничений), технические требования к посадке по СП 82.13330.2016, ограничения и допущения; текст от LLM — только приложением с пометкой «текст ИИ — проверить». Нарушения, ведомость и характеристики пересчитываются на сервере по присланной сцене. Кнопка на панели GreenPlan.

### 6.4 Retrieval-корпус (`data/pattern_corpus.yaml`, `backend/greenplan/pattern_corpus.py`)

34 проекта: 14 реальных (реальный DXF + `design_rationale.md` с цитатой из реальной пояснительной записки, откуда взят паттерн) и 20 синтетических эталонов `21_…_primer`–`30_…_primer` — законченные образцы приёмов, которых среди реальных нет или мало: шумозащитная полоса вдоль дороги, круглая площадь с клумбой и лучами, двор с детской площадкой, бульвар, дом в строгом обрамлении, сад диагональных полос (одна полоса — один вид), волновой сад, регулярный сад квадратов с дубами, озеленённая парковка, сквер над инженерными сетями; и 10 фрагментов улиц с жилыми домами и подъездами (`31_…`–`40_…`): улица с палисадниками, с магазинами на первых этажах, угловой квартал, дом с двором за ним, таунхаусы, поликлиника со сквером у входа, длинный дом вдоль проезда, улица с разделительной полосой, с велодорожкой, тупик с разворотной площадкой. Их собирает генератор `tools/primers/build_primers.py` (`make primers`; уличные — `street_primers.py`): дорожки, сети, МАФ и посадки конкретных видов (вид — в имени слоя DXF), и каждая посадка и МАФ проверяются по тем же нормам, что и GreenPlan, — нарушений в эталонах нет (тест `test_primers.py`). `design_rationale.md` каждого — описание замысла, помеченное как синтетическое; его пересказ — `source_quote` в `data/pattern_corpus.yaml`, из которого LLM пишет «по аналогии с проектом X». Поиск сравнивает по геометрии участка, а не по тому, реальный проект или нет. Самопроверка: каждый проект корпуса находит сам себя как ближайшего соседа (similarity=1.0) — базовый тест retrieval.

Признаки проектов корпуса посчитаны заранее и лежат в `data/pattern_corpus_features.json` вместе с sha256 исходного DXF. Раньше первый запрос GreenPlan в каждом новом процессе разбирал все DXF корпуса (~25 с). Теперь это чтение файла; проект, чей DXF изменился, пересчитывается на лету с предупреждением в логе. После правки DXF корпуса или `characterize_site` файл обновляется командой `make corpus-features`; устаревший файл ловит тест `test_features_file_is_up_to_date`.

### 6.5 Газон (`backend/greenplan/lawn.py`)

«Травянистые покрытия» из ТЗ. Газон в проекте считают площадью (ведомость по форме 9 ГОСТ 21.508: «Газон — 1240 м²»), поэтому GreenPlan не раскладывает плитки, как генератор по сетке, а строит полигоны после расстановки посадок:

- **где:** разрешённые зоны (слои GRASS/LAWN/ГАЗОН и вычисленная парсером открытая земля; если их нет — весь участок) в границе участка, минус твёрдые покрытия и сооружения (здания, проезды, дорожки, площадки, прочие покрытия, запретные охраняемые зоны), минус клумбы кустарника (круг кроны, соседние кусты ряда сливаются в одну клумбу);
- **над сетями — можно:** таблица 9.1 СП 42.13330 и 3.6.1 743-ПП нормируют расстояния только для деревьев и кустарников. Деревья стоят в газоне; приствольные лунки не вычитаются;
- **очистка:** полосы уже 0,5 м и куски меньше 5 м² отбрасываются, контур упрощается с точностью 0,25 м;
- **статус:** часть на существующем покрытии GRASS/LAWN/ГАЗОН — `existing` (сохраняется), остальное — `new`. В ведомость, объём посева и DXF идёт только новый газон;
- **вид:** «Газон обыкновенный», посев из устойчивой травосмеси (ППМ 515-ПП, табл. 4); в записке — нормы высева (СП 82 п. 9.24) и полив 10 л/м² (п. 9.27).

Газон — производная от посадок: записка (`/api/greenplan/document`) и экспорт GreenPlan пересчитывают его по присланной сцене, а не берут из запроса, поэтому ручные правки после GreenPlan учитываются. На 3D-сцене газон рисует `frontend/src/scene/Lawns.tsx` (новый — светлее, существующий — темнее) ярче приглушённо-зелёного основания участка (`Ground.tsx`), так что газон отличим от земли. Сохраняемый газон виден сразу после загрузки чертежа: разбор DXF и пачки DWG отдаёт его в `lawns` (`greenplan/lawn.existing_lawns` — тот же расчёт, только часть `existing`). Если газон выключен в параметрах GreenPlan, новый не добавляется, а газон из чертежа остаётся. На экране газон обновляется при следующем запуске GreenPlan.

### 6.6 Параметры пользователя (`greenplan/options.py`, `greenplan/improvements.py`, `greenplan/pipeline.py`)

Кнопка GreenPlan открывает диалог параметров; без изменений — поведение по умолчанию (стиль по аналогам, деревья, кустарники и газон, без благоустройства). Последние параметры запоминаются, пока открыта вкладка.

- **Существующие насаждения:** «Убрать деревья и кусты с нарушением норм» — до расстановки из сцены убираются исходные деревья и кусты с нарушением отступов (те же нарушения, что в отчёте и подсветке редактора), и их место засаживается заново. В `notes` — сколько убрано и какие отступы нарушены (по типам зон); в DXF места убранных отмечены на слое `USER_REMOVED`, исходный слой не меняется. На `10_stary_gay` из 791 насаждения убираются 84 с нарушениями, правильные не трогаются.

- **Стиль участка:** авто (голосование аналогов), регулярный или пейзажный. Заданный стиль заменяет голосование; ведущий аналог — самый похожий проект этого стиля, если такого нет — зоны получают типовые приёмы стиля.
- **Что сажать:** деревья, кустарники, газон — каждое можно выключить.
- **Предпочтительные виды** деревьев и кустарников: ставятся первыми в любой роли своей категории (ограничение по форме для них снято) и входят в палитру участка. Нормы действуют как для всех: ассортимент для типа территории, 369-ПП, коды ограничений, колючие у дорожек, широкая крона у здания. Почему вид не использован — в `notes` и на панели.
- **Благоустройство** — до посадок, чтобы посадки соблюдали отступы от него:
  - дорожки: каркас дизайна двора (от подъезда к подъезду, к парковке) в дворах участка, до трёх; заводятся зонами `pedestrian_path` шириной 1,5 м (слой `NEW_PATHS` в DXF) — отсюда нормативный отступ посадок (0,7 м для дерева), газон их обходит, вдоль них появляются полосы под изгородь;
  - освещение: фонари через 20 м зигзагом вдоль новых дорожек и снаружи вдоль существующих, не ближе 4 м к деревьям (СП 42, табл. 9.1); в охранные зоны сетей опоры не ставятся — фонарь ищет место на другой стороне или со сдвигом до 8 м, остаток честно отмечается в `notes`;
  - скамейки с урнами: через 30 м вдоль новых дорожек.

Пояснительная записка получает параметры и замечания (раздел 3) и ведомость благоустройства (раздел 4.1); газон, выключенный в параметрах, в записку не попадает.

## 7. Каталог видов и МАФ (`core/plant_catalog.py`)

`CatalogItem`: семантика (`category`, `setback_kind`, `dimensions`) для генератора + внешний вид (`model`, `render`) для фронта. Есть `.glb` — рисуется модель; нет — примитив-заглушка по габаритам (штатный режим, не баг). `catalog_generated.json` — записи из реальных паков моделей (`tools/convert_models.mjs`), дополняет статический каталог, не заменяет. Виды из перечня инвазивных ППМ 369-ПП (`core/invasive_species.py`, 32 вида) из каталога исключаются при загрузке — их не предложит ни один путь.

## 8. Аутентификация и проекты

JWT access (15 мин) + refresh (30 дней, сессия в Redis — реальный отзыв при logout). MongoDB — только `users`/`projects` (постоянное состояние); Redis — то, что не жалко потерять (rate-limit, кэш каталога, сессии). **Fail-open**: недоступен Redis — лимиты/сессии не блокируют работу; недоступна MongoDB — только `/api/projects`/`/api/auth/*` отвечают 503, сам редактор (DXF/генерация/правка текстом) не зависит от БД вовсе. Лимит — 3 проекта на пользователя.

## 9. Экспорт DXF (`exchange/dxf_overlay.py`, `exchange/export_dxf.py`)

ТЗ: исходные слои подосновы, коммуникаций и городской среды не изменяются и не перезаписываются, результат — только на отдельных слоях. Поэтому экспорт дописывает результат **поверх исходного чертежа**, а не собирает DXF из сцены.

- **Хранилище исходников** (`exchange/source_store.py`, каталог `GREENCITY_SOURCES_DIR`, в Docker — том `sources_data`): при загрузке DXF сохраняется сам файл, пачка DWG — сами `.dwg` в порядке загрузки; хранение по sha256, одинаковый файл лежит один раз. В сцене остаётся только `meta.sourceId`.
- **Наложение** (`overlay_scene`): исходник заново разбирается тем же парсером (база), сцена сравнивается с базой по id объектов и зон, и в копию исходника дописываются только отличия — в его координатах и единицах (`X = x / scale + origin.x`, `Y = z / scale + origin.y`, обратное к `parser Transform`). Исходные сущности не трогаются: подписи, штриховки, блоки, размеры и нераспознанные слои остаются как были.
- **Слои результата:** посадка и благоустройство GreenPlan — `NEW_TREE`, `NEW_BUSH`, `NEW_LAWN` (заливка), `NEW_PATHS`, `NEW_LAMP`…; правки пользователя (ИИ-ассистент, панель «Добавить объект», новое место сдвинутого исходного объекта) — `USER_*`; места исходных объектов, которые пользователь удалил или сдвинул, — крестик на `USER_REMOVED` (сам объект в своём слое остаётся); зоны, выделенные в редакторе, — `USER_ZONES`.
- **XDATA `GREENCITY`** на каждой сущности результата: id объекта, вид, происхождение («GreenPlan: приём, аналог» или «правка пользователя»). По id посадка находится в файле объяснений (раздел 9.1).
- **Пачка DWG** при экспорте заново конвертируется тем же конвейером, что и при загрузке, в отдельном процессе (`dwg_job.run_export`): загрузка не платит за сохранение собранного чертежа, платит только экспорт (реальная пачка Харьковской — 18 с).
- **Без исходника** (проект сохранён до появления хранилища, файл удалён, чертёж формата R12) экспорт собирает DXF из сцены (`export_dxf.scene_to_dxf`, в метрах от центра участка, со слоями `NEW_*`/`USER_*`), ответ помечен заголовком `X-GreenCity-Export: rebuilt`, редактор показывает предупреждение.

Сборка из сцены — зеркало парсера: экспортированный план загружается обратно тем же парсером без потери и удвоения посадок. Объекты с `width`+`depth` (мощение/газон/изгородь) — реальным прямоугольником. Severity зон кодируется цветом (AutoCAD Color Index) + XDATA.

### 9.1 Объяснение каждой посадки (`greenplan/explanations.py`, `POST /api/greenplan/explanations`)

ТЗ, п. 8 и 7.2.6: для каждой посадки — объяснение со ссылкой на нормативный акт и пункт, выгружаемое вместе с планом. Кнопки «Объяснения посадок: JSON / CSV» на панели GreenPlan.

- **Каждая новая посадка** (GreenPlan и правки пользователя): вид, координаты в метрах сцены и в координатах исходного чертежа, слой DXF, место на участке и приём, проект-аналог и стиль участка, основание подбора вида (ассортимент Москвы по типу территории, ППМ 515-ПП, без инвазивных ППМ 369-ПП) и до пяти ближайших ограничений — фактическое расстояние, требуемый отступ и пункт НПА, который его задаёт (`setback_norms.setback_basis`: СП 42.13330.2016 табл. 9.1 / 743-ПП табл. 3.6.1, правила по породе — 743-ПП прим. 3, МГСН 1.02-02 п. 4.2.8, СП 82.13330.2016 п. 9.22; опора освещения — СП 42 табл. 9.1). Зазор между соседними объектами — правило планировщика, так и помечено, а не выдаётся за норму.
- **Отклонённые кандидаты:** точки, которые расстановка рассматривала, но не поставила по норме (порода у здания или теплосети, опора освещения, колючие у дорожек), — с причиной и пунктом; собирает `RejectionLog` во время расстановки, подробно до 300 на участок, остальные — счётчиком по правилам.
- **Зоны запрета посадки:** каждое ограничение участка и нормативная полоса вокруг него для дерева и кустарника с пунктом НПА — туда расстановка точки не рассматривает вовсе.
- JSON — полная структура; CSV (разделитель «;», UTF-8 с BOM для Excel) — строка на посадку с ближайшим нормативным ограничением, на отклонённый кандидат и на зону запрета.

## 10. Тесты

Около 1080 тестов (951 в `backend/`, 125 в `parser/`), прогон около минуты (`pytest -n auto`). Лежат по тем же пакетам, что и код (`backend/tests/core/`, `greenplan/`, `text_editor/`, …; `parser/tests/`).

- **Юнит-тесты** на двух семействах фикстур: синтетические (`backend/tests/helpers.py`) — точная геометрия для точных проверок; реальные — `locations/location_old/` и корпус `locations/*` для проверки «расстановка реально не нарушает нормы» на настоящих данных. Независимые проверки норм в тестах считают расстояния сами (через STRtree), а не тем же кодом, что расставлял.
- **Сквозные тесты** (`backend/tests/e2e/`, `make test-e2e`) — настоящее приложение через HTTP на реальных DXF: загрузка → GreenPlan → текст-обоснование → пояснительная записка → экспорт DXF → повторная загрузка (три разных участка); загрузка → правка текстом → генерация → экспорт; регистрация → проект → сохранение результата GreenPlan → обновление токена → выход. Подменены только внешние границы: MongoDB/Redis (`mongomock_motor`/`fakeredis`) и клиенты LLM (фиксированные ответы). Ключи LLM из окружения стираются перед каждым тестом — ни один тест не делает платный запрос.
- **Асинхронность и защита** — `tests/core/test_concurrency.py` (пул потоков, очередь расчётов, отказ при переполнении и по таймауту), `tests/api/test_protection.py` (429 по IP и группам, 413 по `Content-Length` и при потоковой передаче, лимит файлов DWG, 503 с `Retry-After`, закрытый CORS).
- **Сверка с нормативами**: таблица отступов в коде сверяется с `data/norms/sp-42-13330-2016/setbacks.csv`, список конфликтов ассортимента с 369-ПП — с CSV ассортимента.

CI (GitHub Actions и SourceCraft): ruff, oxlint, проверка типов TypeScript, все тесты с покрытием, сборка и запуск Docker-стека.

## 12. Частые вопросы (для защиты)

**Почему не ML/нейросеть?** Датасет — единицы-десятки реальных проектов, для полноценного обучения этого недостаточно и негде проверить обобщение. Вместо этого — retrieval (поиск похожих реальных решений) + детерминированная геометрия; LLM — только для пересказа готовых решений человеческим языком и для понимания просьб в правке текстом (операции, а не координаты), никогда не для координат/паттернов с нуля.

**Что будет под нагрузкой?** Обработчики асинхронные, тяжёлые расчёты идут по одному на процесс uvicorn через ограниченную очередь, запросы к LLM не занимают ни поток, ни очередь. Переполненная очередь даёт 503 с `Retry-After`, а не зависший запрос; частые запросы с одного адреса — 429. Сервер при этом продолжает отвечать на лёгкие запросы. Пропускная способность растёт числом процессов (`UVICORN_WORKERS`), подробности — раздел 2.1.

**Можно ли обратиться к API в обход сайта?** Бэкенд наружу не опубликован, к нему ходит только прокси фронтенда. Через адрес сайта API доступен, как и нужно браузеру, но с лимитами частоты и размера. CORS выключен, Swagger в продакшене выключен.

**Что если LLM недоступна?** Текстовая правка отвечает понятной ошибкой (503), GreenPlan отчёт — `report=null` с `report_error`, сама расстановка (детерминированная часть) не страдает, пояснительная записка формируется без приложения с текстом ИИ.

**Почему нет решений по существующим деревьям и компенсации (Этап 2)?** Для него нужна перечётная ведомость и справочники ценности видов, которых в таблицах датасета нет. Этап не имитируется; в пояснительной записке это указано в разделе «Ограничения и допущения». Сделано только то, что можно проверить по чертежу: по галочке GreenPlan убирает существующие деревья и кусты, которые нарушают нормативные отступы, и засаживает их место заново.

**Считаете ли вы газон?** Да, площадью: GreenPlan строит газон на свободной от покрытий и клумб земле, делит его на новый и сохраняемый, новый идёт в ведомость в м², в DXF (слой `NEW_LAWN`) и в записку с нормами посева и полива. Над инженерными сетями газон допустим — нормы отступов касаются только деревьев и кустарников.

**Откуда берутся виды растений?** Из ассортимента для озеленения Москвы (документ заказчика) — только виды с «+» для типа территории участка, без инвазивных (369-ПП), с учётом кодов ограничений ассортимента и норм по породе; для дворов в приоритете базовый ассортимент 515-ПП. Основание подбора видно на панели GreenPlan и в записке.

**Почему на участке один стиль, а не лучший приём для каждой зоны?** Проектировщик сначала выбирает замысел участка, потом решает зоны в нём. Если выбирать приём для каждой зоны отдельно, в одном дворе оказываются волны рядом с диагоналями. GreenPlan сначала выбирает стиль участка и ведущий аналог, потом приёмы зон в этом стиле, и сажает одну палитру видов на весь участок.

**Как проверяется, что паттерн реально подходит участку?** Retrieval — по числовым признакам (площадь, доля пригодной площади, состав зон), не текстом; назначение паттерна — голосование k ближайших проектов с решением для этого вида зоны (слабые аналогии со сходством ниже 0,2 не голосуют, такие зоны помечены «проверить»), а не один "самый похожий" проект; итоговая расстановка проверяется независимым модулем нарушений (`violation_report.py`), а не тем же кодом, что её строил.

**Почему в корпусе синтетические проекты?** 14 реальных проектов — это то, что реально задокументировано (реальный DXF + реальная пояснительная записка). Среди них нет многих типичных городских случаев (круглая площадь, бульвар, двор с детской площадкой, парковка, сквер над сетями), и новому такому участку не с чем было бы сравниваться. 20 синтетических эталонов закрывают эти случаи законченными образцами без нарушений норм; каждый явно помечен как синтетический.
