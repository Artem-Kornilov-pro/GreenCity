# GreenCity backend

FastAPI-сервис. Два эндпоинта: `POST /api/parse` (DXF → JSON-сцена, готово)
и `POST /api/generate-greenery` (автоматическая расстановка деревьев,
кустов и газона).

Запуск: `make backend` из корня репозитория (или вручную, см. корневой
`README.md`, раздел "Быстрый старт"). Интерактивная документация Swagger --
`http://localhost:8000/docs`, там же можно повызывать `/api/generate-greenery`
руками с разными параметрами без фронтенда.

## POST /api/generate-greenery

### Статус реализации

| Что | Статус |
|---|---|
| Деревья (`type: "tree"`) | ✅ реализовано (`generate_trees()`) |
| Кустарники (`type: "bush"`) | ✅ реализовано (`generate_bushes()`) |
| Газон (`type: "lawn_patch"`) | ✅ реализовано (`generate_lawn()`) |

Все три функции в `greenery_generator.py` независимы по контракту (каждая
принимает `Scene`, возвращает только новые объекты), но эндпоинт вызывает их
**последовательно** -- деревья, потом кусты, потом газон, каждый раз добавляя
результат предыдущего шага в `scene.objects` перед следующим -- иначе,
например, газон лёг бы плиткой поверх уже сгенерированных в этом же запросе
кустов.

### Тело запроса

`Scene` (см. `schemas.py`) -- та же структура, что отдаёт `/api/parse`, плюс
любые правки, которые пользователь уже внёс на фронте (подвинутые/удалённые/
добавленные вручную объекты). Контракт тела **не меняется** этой доработкой --
все новые параметры идут через query string, а не через тело, чтобы не
трогать уже согласованную с фронтендом форму `Scene`.

### Параметры запроса (query string)

Все необязательные -- без них используются дефолты ниже. Их можно задать и
через Swagger UI (`/docs`), и просто в URL:

```
POST /api/generate-greenery?species=Тополь%20чёрный&grid_spacing_m=6&min_tree_spacing_m=5
POST /api/generate-greenery?include_trees=false&include_lawn=false   # только кусты, на готовую сцену
```

| Параметр | Тип | Дефолт | Диапазон | Что делает |
|---|---|---|---|---|
| `species` | `string` | `"Липа мелколистная"` | любая строка | Вид дерева. Пишется в `metadata.species` каждого сгенерированного дерева. Если вид описан в `setback_norms.SPECIES_SETBACK_OVERRIDES` -- для него применяются свои отступы от ограничений (см. ниже "Виды деревьев"); для неизвестных/незаданных видов -- общая норма для `"tree"`. |
| `grid_spacing_m` | `float`, метры | `4.0` | `0.5`–`50.0` (иначе 422) | Шаг регулярной сетки кандидатных точек посадки деревьев. Меньше -- гуще посадка (и дольше считать). Это основной рычаг "слишком много/мало деревьев на демо" -- см. ниже "Плотность посадки". |
| `min_tree_spacing_m` | `float`, метры | `4.0` | `≥ 0` | Минимальное расстояние между стволами уже отобранных сгенерированных деревьев (кандидаты ближе этого расстояния друг к другу отбрасываются). |
| `include_trees` | `bool` | `true` | -- | Добавлять сгенерированные деревья. |
| `include_bushes` | `bool` | `true` | -- | Добавлять сгенерированные группы кустов. |
| `bush_grid_spacing_m` | `float`, метры | `2.5` | `0.5`–`50.0` (иначе 422) | Шаг сетки кандидатных **центров групп** кустов -- отдельно от `grid_spacing_m` у деревьев, у кустов он обычно меньше (см. "Кустарники" ниже). |
| `min_bush_spacing_m` | `float`, метры | `2.5` | `≥ 0` | Минимальное расстояние между ЦЕНТРАМИ групп кустов (не между кустами внутри одной группы -- те специально стоят вплотную). |
| `include_lawn` | `bool` | `true` | -- | Заполнить оставшуюся свободную площадь плиткой газона. |
| `lawn_patch_size_m` | `float`, метры | `4.0` | `1.0`–`10.0` (иначе 422) | Размер стороны плитки газона. |

Значения вне диапазона `*_spacing_m`/`*_size_m` (кроме верхней/нижней
границы, которую FastAPI сам вернёт как `422 Unprocessable Entity`) на
уровне `generate_trees()`/`generate_bushes()`/`generate_lawn()`
дополнительно тихо зажимаются в допустимые границы -- функции безопасны и
при прямом вызове из кода/тестов, в обход HTTP-валидации.

### Тело ответа

`Scene` той же формы, что и запрос: `boundary`/`restrictions`/`windows`/
`canopies`/`meta` возвращаются как есть, `objects` = исходные объекты
пользователя (не тронуты) + новые сгенерированные деревья, кусты и газон.

Раньше эндпоинт был заглушкой и всегда возвращал `null` (фронт трактовал
это как "функция ещё не готова", см. `frontend/src/api.ts`/`App.tsx`).
Теперь алгоритм реализован -- эндпоинт всегда возвращает реальную `Scene`,
даже если новых объектов добавить некуда (пустая допустимая площадь).
`response_model=Optional[Scene]` оставлен в сигнатуре на случай будущих
сценариев, которые лучше явно отличать от "добавили 0 объектов", но сейчас
функция `null` не возвращает.

### Алгоритм: деревья (кратко)

Детерминированный demo-генератор (без ML, см. ТЗ п.16) -- воспроизводимый
результат при одинаковых параметрах и сцене, без случайности.

1. Если у сцены нет `boundary` (или это не полигон) -- вернуть исходную
   сцену без изменений.
2. Собрать **зоны, куда сажать нельзя** (`greenery_generator._keep_out_shapes`):
   зоны `restrictions` с `severity in ("forbidden", "warning")`, каждая
   расширена наружу на отступ, положенный дереву (см. "Отступы" ниже).
   `warning` тоже исключается для автогенератора (парковка, пешеходные
   дорожки и т.п.) -- хотя для **ручного** перетаскивания на фронте
   (`frontend/src/geometry.ts::checkViolations`) это по-прежнему просто
   предупреждение, а не запрет: специально оставлено так, чтобы во время
   презентации можно было руками перетащить дерево на парковку и показать
   жёлтое предупреждение, а не красный запрет. Сюда же добавляется небольшой
   буфер (по умолчанию 1.5 м) вокруг каждого существующего не-здания
   объекта сцены, чтобы не поставить дерево поверх лавочки/фонаря/другого
   дерева.
3. Собрать **явно допустимые зоны озеленения** (`_planting_zone_shapes`):
   зоны с `severity == "allowed"` (газон/лужайка, слой `GRASS`/`LAWN` в
   `parser/parse_dxf.py`). Если такие зоны в сцене размечены -- сажать
   можно только внутри них. Если нет ни одной -- откат на всю площадь
   участка (нестандартная сцена без слоя газона не должна оставаться
   совсем без результата).
4. Итоговая допустимая площадь = (зоны озеленения ∩ участок) − зоны из
   п.2.
5. Сетка кандидатных точек с шагом `grid_spacing_m` по bounding box участка;
   оставляем только точки внутри допустимой площади.
6. Жадный отбор: идём по кандидатам по порядку и берём точку, если она не
   ближе `min_tree_spacing_m` к уже выбранным.
7. Для каждой выбранной точки -- новый `SceneObject`: `id` вида
   `tree_gen_NNN` (нумерация продолжает уже существующие деревья в сцене,
   если они есть), `type: "tree"`, `model: "/models/tree.glb"`,
   `metadata.species`, `metadata.generated: true`, `metadata.reason`
   (список причин размещения в духе ТЗ п.17, например `["внутри допустимой
   зоны озеленения", "0.0 м до ближайшего ограничения (GRASS)"]`).

### Алгоритм: кустарники (`generate_bushes()`)

Тот же каркас, что и у деревьев (п.1-6 выше), с двумя отличиями по смыслу
п.17 ТЗ ("кустарники -- меньшие расстояния и группировка"):

* **меньшие расстояния** -- отступы от зданий/сетей/дорожек у кустарника в
  `setback_norms.SETBACK_NORMS` меньше, чем у дерева (например от здания
  1.5 м вместо 5.0 м, см. таблицу ниже), а буфер вокруг существующих
  объектов сцены (`BUSH_EXISTING_CLEARANCE_M = 0.9`) меньше, чем у дерева
  (`EXISTING_OBJECT_CLEARANCE_M = 1.5`) -- куст компактнее и может стоять
  ближе к лавке/фонарю;
* **группировка** -- сетка кандидатов (шаг `bush_grid_spacing_m`, по
  умолчанию гуще, чем у деревьев) даёт не отдельные кусты, а ЦЕНТРЫ ГРУПП: у
  каждой принятой точки детерминированно (без случайности) раскладываются
  `BUSH_CLUSTER_SIZE = 3` куста по кругу радиуса `BUSH_CLUSTER_RADIUS_M =
  0.6` м -- без проверки расстояния друг с другом внутри группы (это и есть
  группировка, а не редкая россыпь). Группа принимается ЦЕЛИКОМ (все три
  куста внутри допустимой площади) или отклоняется целиком, чтобы не
  оставлять на сцене "осыпавшиеся" группы из одного-двух кустов у самого
  края.

**Плотность.** У кустарника гораздо более мелкий шаг сетки и намного
меньшие отступы, чем у дерева -- на реальном газоне геометрически годных
мест для группы легко набирается несколько тысяч (двор буквально
"закатывается" кустами сплошным ковром без единого просвета газона).
Поэтому после сбора всех годных мест берётся не больше
`MAX_GENERATED_BUSH_CLUSTERS = 60` групп (180 кустов), равномерно
раскиданных по площади (`placement.pick_spread` -- k-средних, та же функция,
что и в `llm_editor.py` для операций правки текстом), а не первые по порядку
обхода сетки -- иначе результат лёг бы одним углом двора.

### Алгоритм: газон (`generate_lawn()`)

Плитки `patch_size_m × patch_size_m` (по умолчанию 4×4 м, как и в каталоге
`plant_catalog.CATALOG`, id `lawn_patch`) на сплошной сетке без зазоров.

В отличие от дерева/кустарника, у газона нет ни `setback_kind` в каталоге,
ни записи в `setback_norms.py` -- у голого дёрна нет ни корней, ни кроны,
поэтому запретные зоны берутся БЕЗ дополнительного отступа по виду посадки
(`_raw_zone_shapes` вместо `_keep_out_shapes`) -- только сама охранная зона,
как её уже разметил парсер. Буфер вокруг существующих объектов тоже
минимальный (`LAWN_EXISTING_CLEARANCE_M = 0.5`) -- плитка вправе подходить
почти вплотную к лавке или стволу дерева.

Каждая плитка проверяется ВСЕМ своим прямоугольником (та же логика, что и у
`Placer.region_contains` в `placement.py`), а не только центром -- иначе
плитка могла бы наполовину висеть над дорожкой при формально верной точке
постановки в центре. Как и у кустов, итоговый список ограничен
(`MAX_GENERATED_LAWN_PATCHES = 150`) и равномерно раскидан по площади через
`pick_spread`, если годных мест больше.

### Отступы и виды деревьев (`setback_norms.py`)

Единый источник правды для нормативных отступов -- `backend/setback_norms.py`,
портирован 1:1 из `frontend/src/setbackNorms.ts` (СНиП 2.07.01-89*/
СП 42.13330.2016). Синхронизация `.py`/`.ts` пока ручная -- при правке
таблицы обнови оба файла.

Базовая таблица (`SETBACK_NORMS`) -- отступ дерева/кустарника от типа зоны,
одинаковый для всех видов дерева:

| Тип зоны | Дерево | Кустарник |
|---|---|---|
| `building` | 5.0 м | 1.5 м |
| `road` | 2.0 м | 1.0 м |
| `gas_pipeline` | 1.5 м | 0 |
| `sewer` | 1.5 м | 0 |
| `water_pipeline` | 2.0 м | 0 |
| `electrical` | 2.0 м | 0.7 м |
| `pedestrian_path` | 0.7 м | 0.5 м |

Для типов зон вне этой таблицы (например `custom`) используется
`minDistance` самой зоны как есть -- без выдумывания цифр, которые нечем
подтвердить.

**Виды деревьев (species).** У разных пород разная агрессивность корневой
системы и размер кроны -- тополю, например, требуется больше места от труб/
фундамента, чем берёзе. Это уже поддержано на уровне интерфейса:
`SPECIES_SETBACK_OVERRIDES: dict[species, dict[zone_type, distance]]`
проверяется ПЕРЕД общей таблицей -- если для `(species, zone_type)` есть
запись, используется она, иначе общая норма для `"tree"`.

Каталог видов сейчас **пуст** -- параметр `species` из query влияет только
на `metadata.species` сгенерированных деревьев, отступы для всех видов пока
одинаковые (общая норма). Чтобы добавить реальный вид с другими
требованиями, достаточно дописать запись в `SPECIES_SETBACK_OVERRIDES` в
`setback_norms.py` -- ни `greenery_generator.py`, ни эндпоинт трогать не
придётся, переопределение подхватится само. Пример (закомментирован в
коде):

```python
SPECIES_SETBACK_OVERRIDES = {
    "тополь чёрный": {"building": 8.0, "sewer": 3.0, "water_pipeline": 3.0},
}
```

### Плотность посадки

Плотность результата определяется тремя факторами вместе:
`grid_spacing_m` (шаг сетки кандидатов), размером самой зоны `allowed`
(газона) в конкретной сцене и `min_tree_spacing_m` (доп. фильтр после
сетки). На тестовом датасете `locations/02_courtyard_3buildings`
(зона газона ~31 800 м²) дефолт `grid_spacing_m=4` даёт ~1500 деревьев --
для презентации может быть избыточно густо; `grid_spacing_m=8` на той же
сцене даёт уже на порядок меньше. Разумного универсального дефолта для всех
масштабов участков не существует -- параметр специально вынесен наружу,
чтобы подбирать под конкретную демо-сцену перед презентацией, а не зашивать
одно число в код.

У кустов и газона та же зависимость от размера сцены есть, но не так видна
в результате: `MAX_GENERATED_BUSH_CLUSTERS`/`MAX_GENERATED_LAWN_PATCHES` в
`greenery_generator.py` ограничивают итоговое число сверху независимо от
того, сколько мест нашла сетка кандидатов (см. "Алгоритм: кустарники/газон"
выше) -- в отличие от деревьев, `bush_grid_spacing_m`/`lawn_patch_size_m`
поэтому не единственный рычаг густоты.
