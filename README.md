Сервис для автоматического проектирования озеленения города с учётом расположения подземных коммуникаций и городской среды (проект для хакатона ЛЦТ).

```

              design_rationale.md с обоснованием паттерна озеленения по каждому) +
              locations/location_old/ — 6 синтетических тестовых участков (от одного

              locations/00_empty_plot/ — пустой участок 100×70 м без построек и
              посадок, для ручной расстановки в редакторе и прогона автогенератора
              с нуля (подробности locations/00_empty_plot/README.md)
data/norms/   нормативы в машиночитаемом виде (отступы, ассортимент 515-ПП/616-ПП,
              инвазивные виды 369-ПП) — подробности data/norms/README.md
parser/       DXF -> JSON (parse_dxf.py): границы участка, зоны ограничений, объекты
converters/   GeoJSON / SHP / DWG -> DXF (для внешних источников данных)

```

## Быстрый старт

Для правки плана текстом нужен ключ LLM (Yandex Cloud). Скопируйте шаблон и заполните значения — сам `.env` в git не попадает:

```bash
cp .env.example .env
```

Без `.env` всё остальное работает, а правка текстом отвечает понятной ошибкой. То же самое с аккаунтами: без MongoDB/Redis (см. ниже) регистрация и вход отвечают понятной ошибкой, а не роняют бэкенд — сам редактор (DXF, генерация, правка текстом) от них не зависит вовсе.

### Вариант A: Docker (основной способ запуска)

```bash
docker compose up -d --build
```

Поднимет весь проект разом, восемь сервисов: backend (`http://localhost:8000`), frontend (`http://localhost:5173`), MongoDB (аккаунты и проекты, `backend/db.py`), Redis (ограничение частоты входа, кэш каталога, сессии по refresh-токенам, `backend/cache.py`) и стек наблюдаемости — Prometheus, Loki, Promtail и Grafana (`http://localhost:3001`, логин/пароль `admin`/`admin`) с готовыми дашбордами метрик и логов, подробности — `observability/README.md`. У каждого сервиса — healthcheck и `depends_on` по нему же (например, backend стартует, только когда mongo/redis реально приняли первое подключение, а не просто "контейнер запущен"; grafana — когда prometheus и loki реально готовы), и `restart: unless-stopped` — сервис, упавший сам по себе (а не остановленный командой), Docker поднимает заново автоматически. Код смонтирован volume'ами — правки в `backend/`, `parser/`, `frontend/` подхватываются на лету (uvicorn `--reload`, vite dev server), без пересборки образа. Это касается только кода: **новые зависимости** в `requirements.txt` так не подхватываются — после их изменения нужен `docker compose up -d --build backend`, иначе бэкенд упадёт на импорте.

По умолчанию backend работает одним процессом (`UVICORN_WORKERS=1` в `docker-compose.yml`) — так работает `--reload`, совмещать его с несколькими процессами uvicorn не умеет. Для нагрузочных прогонов и продакшена стоит поднять до числа свободных ядер (`UVICORN_WORKERS=4`): генерация озеленения и разбор DXF — это чистая CPU-геометрия на shapely, потоками она не распараллеливается (весь Python-код в процессе идёт через один GIL), и настоящий параллелизм здесь дают только отдельные процессы.

Прямые ссылки на готовые дашборды Grafana (логин/пароль `admin`/`admin` при первом переходе):
- Обзор (HTTP + бизнес-метрики): http://localhost:3001/d/greencity-overview
- Логи: http://localhost:3001/d/greencity-logs

Если при первой сборке `docker pull` какого-то образа падает с `authentication required`/`toomanyrequests` — это временное ограничение частоты анонимных запросов к Docker Hub (не проблема самого проекта, проверено — повторный `docker pull` того же образа сразу проходит); помогает повторить команду через пару минут или выполнить `docker login` (у авторизованных лимит выше).

### Вариант B: локально

#### 1. Python-окружение (parser, converters, backend)

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

Для конвертации `.dwg` дополнительно нужен LibreDWG (`brew install libredwg` / `apt install libredwg-tools`).

#### 2. Backend

```bash
source .venv/bin/activate
cd backend
uvicorn main:app --reload --port 8000
```

Эндпоинты: `POST /api/parse` — принимает `.dxf`, отдаёт `{boundary, restrictions, objects, windows, canopies, meta}`; `POST /api/parse-dwg` — то же самое, но на входе папка из нескольких `.dwg` (issue #50): каждый файл конвертируется в DXF через `dwg2dxf`/LibreDWG и сливается в один документ на бэкенде, файлы, которые не удалось прочитать, попадают в `dwgConversionWarnings` ответа, а не роняют весь запрос; `POST /api/generate-greenery` — принимает сцену того же формата (+ опциональные `species`/`grid_spacing_m`/`min_tree_spacing_m`/`bush_grid_spacing_m`/`min_bush_spacing_m`/`lawn_patch_size_m`/`include_trees`/`include_bushes`/`include_lawn` через query string), возвращает её же с добавленными деревьями, группами кустов и газоном (детерминированный генератор по сетке, без ML). Полное описание алгоритма и параметров — `backend/README.md`. `GET /api/catalog` — каталог видов посадок и МАФ. `POST /api/edit-with-text` — принимает `{scene, instruction}`, правит план текстом через LLM. `POST /api/export-dxf` — принимает сцену, отдаёт файл `.dxf` (`backend/export_dxf.py`) — зеркало `/api/parse`, слои и геометрия узнаваемы при повторном импорте тем же парсером.

#### 3. Frontend

```bash
cd frontend
npm install
npm run dev
```

Открыть `http://localhost:5173`, загрузить DXF (например, из `locations/`), кликнуть по дереву/кусту/лавке/фонарю — выбрать и перетащить.

## Линтеры

```bash
make lint        # всё сразу: Python + фронтенд
make lint-py     # только Python — ruff, конфиг в pyproject.toml
make lint-web    # только фронтенд — oxlint, конфиг в frontend/.oxlintrc.json
make lint-fix    # автоисправление того, что чинится автоматически
```

Обе цели возвращают ненулевой код при любой находке (у oxlint для этого включён `--deny-warnings`), поэтому `make lint` годится как гейт в CI. Линтер для Python ставится в venv из `requirements-dev.txt` — отдельно от `requirements.txt`, чтобы не тащить его в backend-образ.

Форматтер (`ruff format`) намеренно не подключён: в конфигах парсера и генераторов (`POLYGON_RULES` и т.п.) таблицы выровнены вручную для читаемости, автоформат бы их развалил.

## Что умеет прототип сейчас

- Парсинг DXF в структурированную сцену: граница участка, здания (с фасадами — окна/козырьки/подъезды), зоны ограничений (коммуникации, дороги, парковки и т.д.), точечные объекты озеленения
- 3D-просмотр сцены с подсветкой зон по степени ограничения (запрещено / предупреждение / разрешено)
- Пак реальных 3D-моделей (`frontend/public/models/`, подробности и как добавить свой — README там же): 31 дерево и 15 МАФ (шезлонги, лавки, стол, стулья, табурет); вид из каталога без модели рисуется примитивом-заглушкой по габаритам — штатный режим
- Отступы посадок по СП 42.13330.2016 (табл. 9.1) и ППМ 743-ПП (табл. 3.6.1): разные для дерева и кустарника (от здания — 5 м и 1.5 м, от трубопроводов и кабелей — 1.5–2 м), плюс правила по породе — липе и клёну 10 м от здания, колючим кустарникам 2 м от дорожек (СП 82), чувствительным к прогреву породам до 4 м от теплосети (МГСН 1.02-02). Кольца отступов видны вокруг зданий и проверяются при перетаскивании
- Редактирование расположения деревьев/кустов/лавок/фонарей с проверкой нарушений отступов в реальном времени
- Экспорт отредактированного расположения объектов в JSON
- Экспорт итогового плана обратно в DXF (кнопка "Экспорт DXF" → `/api/export-dxf`, `backend/export_dxf.py`): границы, здания, зоны ограничений, все посадки и МАФ с реальными габаритами (мощение/изгородь/газон/клумба — прямоугольником, не точкой) — файл открывается в любом CAD, а слои названы так, что при желании читаются обратно тем же `parser/parse_dxf.py`
- Конвертация GeoJSON/SHP/DWG в DXF для импорта внешних геоданных (Мосгеотрест, data.mos.ru)
- Кнопка "Сгенерировать растительность автоматически" → `/api/generate-greenery`: последовательно расставляет деревья по сетке, группы кустов (по несколько вплотную, п.17 ТЗ: "меньшие расстояния и группировка") и сплошной газон плитками на оставшейся свободной площади — всё внутри зон газона, обходя здания/коммуникации/парковки/дорожки с нужным по нормам отступом; не трогает уже расставленные пользователем объекты (`backend/greenery_generator.py`, `backend/setback_norms.py`)
- Правка плана текстом через LLM (ТЗ: корректировки в текстовом формате). Задача разбита на два уровня: модель выбирает намерение, виды и параметры, а координаты считает детерминированный планировщик (`backend/placement.py`). Планировщик сам берёт шаг по размеру вида и держит отступы по нормам: от зданий, сетей, дорожек, парковок, фонарей (дерево — 4 м от опоры освещения) и подъездов; объект с нарушением сдвигает в ближайшее допустимое место (не дальше 10 м), а если такого нет — отклоняет с причиной (`backend/llm_editor.py`). Операции:
  - Точечные: `add`/`remove`/`move`/`rotate` — для конкретных объектов.
  - Ряды и группы: `place_along` (вдоль дорожек/фасадов/парковок/площадок/периметра), `place_in_area` (у точки или равномерно по области), `cover_area` (сплошной ковёр газона/цветника — в отличие от `place_in_area`, плитки укладываются встык, а не редкой россыпью), `line_of` (линия объектов между двумя произвольными точками/объектами/целями — обобщение `connect`), `enclose` (кольцо вокруг объекта/цели/точки).
  - Правка существующих объектов: `remove_where` (можно без списка типов — «очисти эту зону», чем бы она ни была занята), `replace_where` (замена вида без смены места), `thin_out` (прореживание слишком плотной посадки), `resize` (масштаб), `face` (разворот к точке/объекту), `align_along` (подровнять сбившийся ряд), `duplicate_near` (копия рядом с другим местом), `set_count` (довести число объектов до N).
  - `connect` — дорожка между двумя точками/объектами/целями (например «от подъезда к фонтану», «сеть дорожек — с парковкой»). Прямую, перекрытую зданием, планировщик не отклоняет — сначала пробует обойти препятствие по кратчайшему пути (граф видимости вокруг углов препятствий + Дейкстра, `placement.shortest_path`).
  - `define_zone` — выделить именованную зону («детская зона», «здесь ничего не сажать»): круг вокруг точки/объекта/цели, сразу попадает в зоны ограничений (видна на плане, учитывается всеми правками) и адресуется по имени в `target` любой операции и в `area` у `place_in_area`/`cover_area` — так решается «выдели зону под сад и посади там кусты».
  - `design_area` — полный дизайн двора одной операцией: каркас дорожек (от подъезда к подъезду, с выходом на парковку, если она рядом), фонари и скамейки с урнами вдоль дорожек, живая изгородь по краю, деревья вразброс по свободной площади; фонтан и площадь — только по явной просьбе и там, где для них реально есть место (`backend/courtyard_design.py`).

  Провайдер выбирается переменной `LLM_PROVIDER` в `.env` — `gemini` (по умолчанию) или `yandex`, оба через OpenAI-совместимый API (`backend/llm_editor.py`); ответ приходит за несколько секунд
- Запуск в Docker (`docker compose up -d --build`) — healthcheck на каждом сервисе, зависимости по факту готовности (`depends_on: condition: service_healthy`), автоматический перезапуск упавшего контейнера (`restart: unless-stopped`)
- Наблюдаемость: метрики Prometheus (стандартные HTTP + бизнес-метрики — сколько распарсено/сгенерировано/экспортировано, исходы правки текстом и входа/регистрации) и структурированные JSON-логи с request_id, дашборды Grafana готовы из коробки — поднимаются вместе со всем остальным одной командой `docker compose up`, подробности `observability/README.md`

## GreenPlan (issue #23) — генеративное озеленение по прошлым проектам

Параллельно с ручным редактором развивается детерминированный конвейер, который
предлагает озеленение участка не с нуля, а по аналогии с тем, что реально делали
архитекторы на похожих проектах — без ML-тренировки, без LLM-координат. Полный
алгоритм — 7 этапов, статус по каждому:

| Этап | Что делает | Статус |
|---|---|---|
| 0. Справочники | Нормативы отступов, ассортимент, инвазивные виды в машиночитаемом виде | `data/norms/` — готово; каталог видов/кодов решений из xlsm заказчика — нет |
| 1. Импорт DWG→DXF | Конвертация + классификация слоёв по подстрокам (`parser/parse_dxf.py`) | Готово; джойн перечётной ведомости с деревьями по номеру — нет |
| 2. Применение решений | Вырубить/сохранить/пересадить + расчёт компенсации | Не начато |
| 3. Характеризация + retrieval | Признаки участка (`backend/site_characterization.py`) + поиск похожих проектов (`backend/pattern_retrieval.py`) | Готово — retrieval-корпус: 14 задокументированных проектов `locations/*`, не полные 20 из ТЗ (второй корпус ещё не восстановлен) |
| 4. Назначение паттернов | Разбиение на геометрические зоны (`backend/zone_partitioning.py`) + голосование ближайших соседей за паттерн (`backend/pattern_assignment.py`, `data/pattern_corpus.yaml`) | Готово правилами; опциональное ранжирование локальной LLM — нет |
| 5. Расстановка | Точки/ряды/кластеры через геометрический планировщик (`backend/deterministic_placement.py`, переиспользует `backend/placement.py`) | Готово |
| 6. Отчёт решений | Список нарушений и ассортимент (`backend/violation_report.py`/`assortment_report.py`) + текст-объяснение через локальную LLM (`backend/decision_report.py`) | Готово |

`POST /api/greenplan/generate` (быстро, без LLM) и `POST /api/greenplan/report`
(текст-объяснение, ~30с через Ollama, отдельным запросом) уже подключены к
фронтенду — подробности в `docs/TECHNICAL_OVERVIEW.md`, раздел 6.2.
