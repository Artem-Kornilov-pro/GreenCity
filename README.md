Сервис для автоматического проектирования озеленения города с учётом расположения подземных коммуникаций и городской среды (проект для хакатона ЛЦТ).

  text_editor/   правка плана текстом через LLM и дизайн двора (design_area)

                 (src/pages/editor/ -- страница редактора и её панели)

## Быстрый старт

Обе LLM проекта — в Yandex AI Studio, с одним ключом и каталогом (`YANDEX_CLOUD_API_KEY`, `YANDEX_CLOUD_FOLDER`): ИИ-ассистент — Qwen3 235B (`YANDEX_CLOUD_MODEL`), текст-обоснование GreenPlan — YandexGPT 5.1 Pro (`YANDEX_CLOUD_REPORT_MODEL`). Для ассистента можно переключиться на Gemini (`LLM_PROVIDER=gemini`). Скопируйте шаблон и заполните значения — сам `.env` в git не попадает:

```bash
cp .env.example .env
```

Без `.env` всё остальное работает, а правка текстом отвечает понятной ошибкой; без ключа Yandex GreenPlan расставляет посадки и формирует пояснительную записку, но без текста-обоснования. То же самое с аккаунтами: без MongoDB/Redis (см. ниже) регистрация и вход отвечают понятной ошибкой, а не роняют бэкенд — сам редактор (DXF, генерация, правка текстом) от них не зависит вовсе.

### Вариант A: Docker (основной способ запуска)

```bash
docker compose up -d --build
```

Поднимет весь проект разом, восемь сервисов: backend (`http://localhost:8000`), frontend (`http://localhost:5173`), MongoDB (аккаунты и проекты, `backend/storage/db.py`), Redis (ограничение частоты входа, кэш каталога, сессии по refresh-токенам, `backend/storage/cache.py`) и стек наблюдаемости — Prometheus, Loki, Promtail и Grafana (`http://localhost:3001`, логин/пароль `admin`/`admin`) с готовыми дашбордами метрик и логов, подробности — `observability/README.md`. У каждого сервиса — healthcheck и `depends_on` по нему же (например, backend стартует, только когда mongo/redis реально приняли первое подключение, а не просто "контейнер запущен"; grafana — когда prometheus и loki реально готовы), и `restart: unless-stopped` — сервис, упавший сам по себе (а не остановленный командой), Docker поднимает заново автоматически. Код смонтирован volume'ами — правки в `backend/`, `parser/`, `frontend/` подхватываются на лету (uvicorn `--reload`, vite dev server), без пересборки образа. Это касается только кода: **новые зависимости** в `requirements.txt` так не подхватываются — после их изменения нужен `docker compose up -d --build backend`, иначе бэкенд упадёт на импорте.

Это дев-режим: по умолчанию backend работает одним процессом с `--reload` (`UVICORN_WORKERS=1`, `UVICORN_RELOAD=1` в `docker-compose.yml`), совмещать `--reload` с несколькими процессами uvicorn не умеет. Для нагрузочных прогонов и продакшена стоит поднять до числа свободных ядер (`UVICORN_WORKERS=4`): генерация озеленения и разбор DXF — это чистая CPU-геометрия на shapely, потоками она не распараллеливается (весь Python-код в процессе идёт через один GIL), и настоящий параллелизм здесь дают только отдельные процессы.

Прямые ссылки на готовые дашборды Grafana (логин/пароль `admin`/`admin` при первом переходе):
- Обзор (HTTP + бизнес-метрики): http://localhost:3001/d/greencity-overview
- Логи: http://localhost:3001/d/greencity-logs

Если при первой сборке `docker pull` какого-то образа падает с `authentication required`/`toomanyrequests` — это временное ограничение частоты анонимных запросов к Docker Hub (не проблема самого проекта, проверено — повторный `docker pull` того же образа сразу проходит); помогает повторить команду через пару минут или выполнить `docker login` (у авторизованных лимит выше).

### Вариант A2: Docker на сервере (продакшен-режим)

```bash
make docker-prod-up   # docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build
```

Поверх того же `docker-compose.yml` (`docker-compose.prod.yml`):
- **frontend** — статическая сборка за nginx (`frontend/Dockerfile.prod`) на порту 80 вместо vite dev server; `/api/` nginx проксирует на backend, сайт и API на одном адресе;
- **backend** — код из образа, без смонтированных каталогов и без `--reload`, `UVICORN_WORKERS` процессов (3); наружу не открыт, только через nginx;
- **mongo** — кеш ограничен 0,5 ГБ;
- образ backend — без исходных материалов участков (`locations/*/data`, 56 МБ PDF и сканов): бэкенду нужны только DXF и `design_rationale.md`.

Ответы API сжимаются (gzip): сцена реального участка — 1–13 МБ JSON, в сжатом виде в 5–6 раз меньше.

Продакшен-режим рассчитан на сервер **4 vCPU (2 ГГц) / 8 ГБ ОЗУ / 40 ГБ SSD** (LLM — облачные, по API):

| Сервис | Память | CPU |
|---|---|---|
| backend, 3 процесса | до 4 ГБ (до ~750 МиБ на процесс на крупном участке; разбор DWG — до 2 пачек одновременно, ~0,75 ГБ + 3 процесса по ~0,5 ГБ на пачку) | 3 ядра |
| MongoDB, кеш 0,5 ГБ | до 1 ГБ | — |
| Redis | до 256 МБ | — |
| frontend (nginx) | до 128 МБ | — |
| мониторинг и система | ~1,4 ГБ | четвёртое ядро |

Узкое место — процессор: один тяжёлый запрос занимает одно ядро, при 2 ГГц GreenPlan считается 2–10 с на обычном участке и до ~30 с на участке в 2 км². Три процесса — три тяжёлых запроса одновременно; четвёртое ядро оставлено базе, nginx и мониторингу, чтобы сайт отвечал под нагрузкой. Логи контейнеров ограничены (3 файла по 10 МБ на сервис), старые образы и кеш сборки после обновлений удаляет `make docker-prune`.

На другом сервере число процессов меняется переменной (около 750 МиБ памяти на процесс):

```bash
UVICORN_WORKERS=2 make docker-prod-up
```

### Вариант B: локально

#### 1. Python-окружение (parser, converters, backend)

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

Для конвертации `.dwg` дополнительно нужен LibreDWG (`brew install libredwg` / `apt install libredwg-tools`).

#### 2. Backend

```bash
source .venv/bin/activate
cd backend
uvicorn main:app --reload --port 8000
```

Эндпоинты: `POST /api/parse` — принимает `.dxf`, отдаёт `{boundary, restrictions, objects, windows, canopies, meta}`; `POST /api/parse-dwg` — то же самое, но на входе папка из нескольких `.dwg` (issue #50): каждый файл конвертируется в DXF через `dwg2dxf`/LibreDWG и сливается в один документ на бэкенде, файлы, которые не удалось прочитать, попадают в `dwgConversionWarnings` ответа, а не роняют весь запрос; `POST /api/generate-greenery` — принимает сцену того же формата (+ опциональные `species`/`grid_spacing_m`/`min_tree_spacing_m`/`bush_grid_spacing_m`/`min_bush_spacing_m`/`lawn_patch_size_m`/`include_trees`/`include_bushes`/`include_lawn` через query string), возвращает её же с добавленными деревьями, группами кустов и газоном (детерминированный генератор по сетке, без ML). Полное описание алгоритма и параметров — `backend/README.md`. `GET /api/catalog` — каталог видов посадок и МАФ. `POST /api/edit-with-text` — принимает `{scene, instruction, history}`, правит план текстом через LLM. `POST /api/export-dxf` — принимает сцену, отдаёт `.dxf`: исходный чертёж без изменений плюс слои результата `NEW_*` (GreenPlan) и `USER_*` (правки пользователя) в его координатах (`backend/exchange/dxf_overlay.py`). `POST /api/greenplan/explanations` — объяснение каждой посадки со ссылкой на НПА и пункт (JSON или CSV).

#### 3. Frontend

```bash
cd frontend
npm install
npm run dev
```

Открыть `http://localhost:5173`, загрузить DXF (например, из `locations/`), кликнуть по дереву/кусту/лавке/фонарю — выбрать и перетащить.

## Тесты

```bash
make test        # все тесты backend/ и parser/, параллельно (pytest-xdist)
make test-e2e    # только сквозные сценарии (backend/tests/e2e)
make test-cov    # всё + отчёт о покрытии
```

Около 1000 тестов, прогон ~1 минута. Тесты лежат по тем же пакетам, что и код (`backend/tests/core/`, `greenplan/`, `text_editor/`, …; `parser/tests/`). Сквозные тесты (`backend/tests/e2e/`) гоняют настоящее приложение через HTTP на реальных DXF из `locations/`: загрузка → GreenPlan → текст-обоснование → пояснительная записка → экспорт DXF → повторная загрузка; загрузка → правка текстом → генерация → экспорт; регистрация → проект → сохранение результата → выход. Подменены только внешние границы: MongoDB и Redis (in-memory), облачные LLM Yandex AI Studio — правка текстом и текст-обоснование (фиксированные ответы). Ни один тест не обращается к платному API. Качество ИИ-ассистента на настоящей модели проверяет отдельный инструмент `tools/ai_editor_eval/run.py` (платные запросы, запускается вручную; см. `docs/TECHNICAL_OVERVIEW.md`, раздел 5.2).

CI (GitHub Actions и SourceCraft) запускает ruff, oxlint, проверку типов TypeScript и все тесты.

## Линтеры

```bash
make lint        # всё сразу: Python + фронтенд
make lint-py     # только Python — ruff, конфиг в pyproject.toml
make lint-web    # только фронтенд — oxlint, конфиг в frontend/.oxlintrc.json
make lint-fix    # автоисправление того, что чинится автоматически
```

Обе цели возвращают ненулевой код при любой находке (у oxlint для этого включён `--deny-warnings`), поэтому `make lint` годится как гейт в CI. Линтер для Python ставится в venv из `requirements-dev.txt` — отдельно от `requirements.txt`, чтобы не тащить его в backend-образ.

Форматтер (`ruff format`) намеренно не подключён: в конфигах парсера и генераторов (`POLYGON_RULES` и т.п.) таблицы выровнены вручную для читаемости, автоформат бы их развалил.

## Что умеет прототип сейчас

- Парсинг DXF в структурированную сцену: граница участка, здания (с фасадами — окна/козырьки/подъезды), зоны ограничений (коммуникации, дороги, парковки и т.д.), точечные объекты озеленения
- 3D-просмотр сцены с подсветкой зон по степени ограничения (запрещено / предупреждение / разрешено)
- Пак реальных 3D-моделей (`frontend/public/models/`, подробности и как добавить свой — README там же): 31 дерево и 15 МАФ (шезлонги, лавки, стол, стулья, табурет); вид из каталога без модели рисуется примитивом-заглушкой по габаритам — штатный режим
- Отступы посадок по СП 42.13330.2016 (табл. 9.1) и ППМ 743-ПП (табл. 3.6.1): разные для дерева и кустарника (от здания — 5 м и 1.5 м, от трубопроводов и кабелей — 1.5–2 м), плюс правила по породе — липе и клёну 10 м от здания, колючим кустарникам 2 м от дорожек (СП 82), чувствительным к прогреву породам до 4 м от теплосети (МГСН 1.02-02). Кольца отступов видны вокруг зданий и проверяются при перетаскивании
- Редактирование расположения деревьев/кустов/лавок/фонарей с проверкой нарушений отступов в реальном времени
- Экспорт отредактированного расположения объектов в JSON
- Экспорт итогового плана обратно в DXF (кнопка "Экспорт DXF" → `/api/export-dxf`): результат дописывается поверх исходного чертежа — исходные слои, подписи, блоки и координаты не меняются, посадка GreenPlan — на слоях `NEW_*`, правки пользователя — `USER_*`, у каждой сущности результата XDATA с id посадки
- Объяснение каждой посадки со ссылкой на пункт НПА (кнопки «Объяснения посадок: JSON / CSV» на панели GreenPlan, `backend/greenplan/explanations.py`): вид, приём и аналог, основание подбора вида, ближайшие ограничения с расстоянием и нормой, отклонённые по нормам точки, зоны запрета посадки
- Конвертация GeoJSON/SHP/DWG в DXF для импорта внешних геоданных (Мосгеотрест, data.mos.ru)
- Кнопка GreenPlan — автоозеленение по аналогии с похожими реализованными проектами (раздел ниже): приём озеленения для каждой зоны участка, виды из ассортимента Москвы для типа территории, расстановка с проверкой норм, газон в м² (на сцене, в ведомости и в DXF на слое `NEW_LAWN`), текст-обоснование и пояснительная записка в DOCX с ведомостью по форме 9 ГОСТ 21.508
- Параметры GreenPlan перед запуском: стиль участка (авто, регулярный, пейзажный), что сажать (деревья, кустарники, газон), предпочтительные виды деревьев и кустарников (в пределах норм и ассортимента) и благоустройство — дорожки во дворах, освещение, скамейки с урнами; повторный запуск заменяет прошлый результат
- Загрузка папки проекта с `.dwg`-файлами (конвертация на сервере через LibreDWG, `backend/exchange/dwg_batch_converter.py`)
- Генератор по сетке `/api/generate-greenery` — деревья, группы кустов и газон плитками внутри зон газона с нормативными отступами (`backend/generation/`). В интерфейсе кнопки для него нет (его заменил GreenPlan), доступен через API и Swagger (`/docs`)
- Виды из перечня инвазивных растений ППМ 369-ПП исключены из каталога: их не предложат ни GreenPlan, ни правка текстом, ни панель «Добавить объект»
- Правка плана текстом через LLM (ТЗ: корректировки в текстовом формате). Задача разбита на два уровня: модель выбирает намерение, виды и параметры, а координаты считает детерминированный планировщик (`backend/core/placement.py`). Планировщик сам берёт шаг по размеру вида и держит отступы по нормам: от зданий, сетей, дорожек, парковок, фонарей (дерево — 4 м от опоры освещения) и подъездов; объект с нарушением сдвигает в ближайшее допустимое место (не дальше 10 м), а если такого нет — отклоняет с причиной (`backend/text_editor/service.py`). Операции:
  - Точечные: `add`/`remove`/`move`/`rotate` — для конкретных объектов.
  - Ряды и группы: `place_along` (вдоль дорожек/фасадов/парковок/площадок/периметра), `place_in_area` (у точки или равномерно по области), `cover_area` (сплошной ковёр газона/цветника — в отличие от `place_in_area`, плитки укладываются встык, а не редкой россыпью), `line_of` (линия объектов между двумя произвольными точками/объектами/целями — обобщение `connect`), `enclose` (кольцо вокруг объекта/цели/точки).
  - Правка существующих объектов: `remove_where` (можно без списка типов — «очисти эту зону», чем бы она ни была занята), `replace_where` (замена вида без смены места), `thin_out` (прореживание слишком плотной посадки), `resize` (масштаб), `face` (разворот к точке/объекту), `align_along` (подровнять сбившийся ряд), `duplicate_near` (копия рядом с другим местом), `set_count` (довести число объектов до N).
  - `connect` — дорожка между двумя точками/объектами/целями (например «от подъезда к фонтану», «сеть дорожек — с парковкой»). Прямую, перекрытую зданием, планировщик не отклоняет — сначала пробует обойти препятствие по кратчайшему пути (граф видимости вокруг углов препятствий + Дейкстра, `placement_geometry.shortest_path`).
  - `define_zone` — выделить именованную зону («детская зона», «здесь ничего не сажать»): круг вокруг точки/объекта/цели, сразу попадает в зоны ограничений (видна на плане, учитывается всеми правками) и адресуется по имени в `target` любой операции и в `area` у `place_in_area`/`cover_area` — так решается «выдели зону под сад и посади там кусты».
  - `design_area` — полный дизайн двора одной операцией: каркас дорожек (от подъезда к подъезду, с выходом на парковку, если она рядом), фонари и скамейки с урнами вдоль дорожек, живая изгородь по краю, деревья вразброс по свободной площади (виды по умолчанию — из ассортимента Москвы для дворов, как у GreenPlan); фонтан и площадь — только по явной просьбе и там, где для них реально есть место (`backend/text_editor/courtyard_design.py`).

  - `run_greenplan` — «озелени участок в регулярном стиле, побольше лип»: модель выбирает параметры GreenPlan, а фронтенд запускает его с панелью решений и пояснительной запиской.

  Виды можно называть по-русски («липы», «сирень», «клён остролистный») — названные в просьбе виды всегда попадают в контекст модели. Ассистент помнит последние правки чата («убери их», «то же самое у второго дома»), а последнюю правку можно отменить кнопкой в чате.

  Провайдер выбирается переменной `LLM_PROVIDER` в `.env` — `yandex` (по умолчанию, Yandex AI Studio, модель Qwen3 235B) или `gemini`, оба через OpenAI-совместимый API (`backend/text_editor/service.py`, `backend/core/yandex_ai.py`); ответ приходит за несколько секунд
- Запуск в Docker (`docker compose up -d --build`) — healthcheck на каждом сервисе, зависимости по факту готовности (`depends_on: condition: service_healthy`), автоматический перезапуск упавшего контейнера (`restart: unless-stopped`)
- Наблюдаемость: метрики Prometheus (стандартные HTTP + бизнес-метрики — сколько распарсено/сгенерировано/экспортировано, исходы правки текстом и входа/регистрации) и структурированные JSON-логи с request_id, дашборды Grafana готовы из коробки — поднимаются вместе со всем остальным одной командой `docker compose up`, подробности `observability/README.md`

## GreenPlan (issue #23) — генеративное озеленение по прошлым проектам

Параллельно с ручным редактором развивается детерминированный конвейер, который
предлагает озеленение участка не с нуля, а по аналогии с тем, что реально делали
архитекторы на похожих проектах — без ML-тренировки, без LLM-координат. Полный
алгоритм — 7 этапов, статус по каждому:

| Этап | Что делает | Статус |
|---|---|---|
| 0. Справочники | Нормативы отступов, ассортимент, инвазивные виды в машиночитаемом виде | Готово (`data/norms/`, 10 актов) |
| 1. Импорт DWG→DXF | Конвертация + классификация слоёв по подстрокам (`parser/parse_dxf.py`) | Готово; джойн перечётной ведомости с деревьями по номеру — нет |
| 2. Применение решений | Вырубить/сохранить/пересадить + расчёт компенсации | Не реализуется: в таблицах датасета нет данных для этого этапа |
| 3. Характеризация + retrieval | Признаки участка (`backend/greenplan/site_characterization.py`) + поиск похожих проектов (`backend/greenplan/pattern_retrieval.py`) | Готово — корпус: 14 реальных проектов + 20 синтетических эталонов для типов участков, которых среди реальных нет |
| 4. Назначение паттернов | Разбиение на геометрические зоны (`backend/greenplan/zone_partitioning.py`); сначала общее решение — стиль участка (регулярный или пейзажный) и ведущий проект-аналог, затем голосование ближайших соседей за приёмы зон в этом стиле (`backend/greenplan/pattern_assignment.py`, `data/pattern_corpus.yaml`); единая палитра видов на участок | Готово правилами; опциональное ранжирование LLM — нет |
| 5. Расстановка | Точки/ряды/кластеры через геометрический планировщик (`backend/greenplan/deterministic_placement.py`, переиспользует `backend/core/placement.py`); виды — по ассортименту Москвы для типа территории, без инвазивных 369-ПП (`backend/greenplan/species_selection.py`); газон площадью на свободной земле, новый и сохраняемый (`backend/greenplan/lawn.py`) | Готово |
| 6. Отчёт решений | Список нарушений и ассортимент (`backend/greenplan/violation_report.py`/`assortment_report.py`) + текст-объяснение через YandexGPT 5.1 Pro (`backend/greenplan/decision_report.py`) + пояснительная записка в DOCX с ведомостью по форме 9 ГОСТ 21.508 (`backend/greenplan/document.py`) | Готово |

`POST /api/greenplan/generate` (быстро, без LLM), `POST /api/greenplan/report`
(текст-объяснение через YandexGPT, отдельным запросом) и
`POST /api/greenplan/document` (пояснительная записка в DOCX) подключены к
фронтенду — подробности в `docs/TECHNICAL_OVERVIEW.md`, раздел 6.3.
